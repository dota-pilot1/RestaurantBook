# 주문 이벤트 생산/소비 정리

## 1. 결론

주문 상태 전파는 `주방 페이지 전용`이 아니라 `주문 도메인 공통 realtime`으로 잡는다.

```txt
고객 키오스크  -> 주문 생성/취소 생산자, 자기 주문 상태 소비자
주방           -> 접수/조리 상태 생산자, 신규 주문 소비자
직원           -> 결제 완료 생산자, 결제 대기 주문 소비자
매니저/관리자  -> 운영 모니터링 소비자, 예외 처리 생산자 후보
```

MVP 상태 흐름:

```txt
RECEIVED -> ACCEPTED -> COOKING -> READY -> COMPLETED
```

상태 의미:

```txt
RECEIVED    주문 생성, 주방 접수 대기
ACCEPTED    주방 접수 완료
COOKING     조리 중
READY       조리 완료, 후불 결제 대기
COMPLETED   후불 결제 완료, 주문 종료
CANCELED    취소
```

`서빙 완료` 상태는 MVP에서 만들지 않는다. `READY` 이후 직원이 알아서 전달하고, 데스크/직원이 결제 완료 시 `COMPLETED`로 종료한다.

주방 UI는 4컬럼 보드로 유지한다.

```txt
접수 대기 -> 접수됨 -> 조리중 -> 조리 완료
```

이 구성은 현재 요구에 충분한 전형적인 주방 처리 흐름이다. 주방은 `READY`까지만 생산하고, `READY` 카드는 직원/데스크 결제 대기 상태로 넘어간다. `서빙 완료`, `픽업 완료`, `PAID` 별도 상태는 MVP에서 제외한다.

## 2. 역할 기준

현재 역할은 유지한다.

```txt
ROLE_ADMIN     시스템 관리자
ROLE_MANAGER   매장 관리자
ROLE_KITCHEN   주방
ROLE_STAFF     직원
ROLE_CUSTOMER  고객
```

`ROLE_STAFF`는 데스크와 서빙을 포함하는 현장 직원이다. 데스크 직원과 서빙 직원을 별도 role로 나누지 않는다. 같은 주문 운영 화면을 보고 같은 결제 완료 액션을 수행하기 때문이다.

`ROLE_MANAGER`는 데스크가 아니라 매장 관리자다. 주문 모니터링, 예외 처리, 운영 관리 권한을 가진다.

## 3. 토픽 설계

운영 화면 공통 토픽:

```txt
orders:operations
```

구독 가능 역할:

```txt
ROLE_ADMIN
ROLE_MANAGER
ROLE_KITCHEN
ROLE_STAFF
```

용도:

- 주방 보드 갱신
- 직원/데스크 주문 화면 갱신
- 매니저/관리자 주문 모니터링 갱신
- 새 주문 사운드/배지 후보

고객 테이블 스코프 토픽:

```txt
customer:orders/{tableName}
```

용도:

- 고객 키오스크의 자기 테이블 active 주문 상태 갱신
- 주문 접수/조리중/조리완료/결제완료 반영

MVP에서는 tableName 기반으로 시작한다. 장기적으로는 테이블 세션 토큰 또는 주문 세션 키로 바꾸는 게 안전하다.

## 4. 이벤트 종류

MVP 필수 이벤트:

```txt
ORDER_LIST_CHANGED
CUSTOMER_ORDERS_CHANGED
```

선택 이벤트:

```txt
NEW_ORDER_RECEIVED
ORDER_STATUS_CHANGED
```

이벤트 의미:

```txt
ORDER_LIST_CHANGED
- orders:operations로 발행
- 운영 화면 목록 재조회 신호
- 주방/직원/매니저 화면이 수신해서 각자 query invalidate

CUSTOMER_ORDERS_CHANGED
- customer:orders/{tableName}로 발행
- 고객 키오스크 active 주문 재조회 신호

NEW_ORDER_RECEIVED
- orders:operations로 발행
- 새 주문 사운드/배지용
- 주문 생성 때만 발행
- MVP UI 후순위

ORDER_STATUS_CHANGED
- orders:operations와 customer:orders/{tableName}에 발행 가능
- 캐시 직접 patch가 필요할 때 사용
- MVP에서는 invalidate 방식이면 없어도 됨
```

권장 MVP:

```txt
초기 구현은 ORDER_LIST_CHANGED, CUSTOMER_ORDERS_CHANGED만 사용한다.
NEW_ORDER_RECEIVED와 ORDER_STATUS_CHANGED는 화면 UX가 필요해질 때 추가한다.
```

## 5. 이벤트 생산자

### 고객 키오스크

생산 액션:

```txt
POST /api/customer/orders
RECEIVED 주문 생성
```

발행:

```txt
orders:operations / ORDER_LIST_CHANGED
customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
```

선택 발행:

```txt
orders:operations / NEW_ORDER_RECEIVED
```

취소가 허용되는 경우:

```txt
PATCH /api/customer/orders/{orderId}/cancel
RECEIVED 또는 ACCEPTED 후보 -> CANCELED
```

발행:

```txt
orders:operations / ORDER_LIST_CHANGED
customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
```

### 주방

생산 액션:

```txt
PATCH /api/kitchen/orders/{orderId}/accept
RECEIVED -> ACCEPTED

PATCH /api/kitchen/orders/{orderId}/start-cooking
ACCEPTED -> COOKING

PATCH /api/kitchen/orders/{orderId}/ready
COOKING -> READY
```

각 상태 변경 후 발행:

```txt
orders:operations / ORDER_LIST_CHANGED
customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
```

### 직원

생산 액션:

```txt
PATCH /api/operations/orders/{orderId}/complete
READY -> COMPLETED
```

의미:

```txt
후불 결제 완료, 주문 종료
```

발행:

```txt
orders:operations / ORDER_LIST_CHANGED
customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
```

### 매니저/관리자

MVP에서는 주 생산자가 아니다. 다만 운영 화면에서 취소/예외 처리를 허용하면 생산자가 될 수 있다.

후보 액션:

```txt
강제 취소
상태 보정
주문 삭제 대신 취소 처리
```

이 경우에도 `OrderBroadcaster`를 통해 같은 이벤트를 발행한다.

## 6. 이벤트 소비자

### 고객 키오스크

구독:

```txt
customer:orders/{tableName}
```

수신 처리:

```txt
CUSTOMER_ORDERS_CHANGED
-> queryClient.invalidateQueries(["customer-active-orders", tableName])
```

화면 반영:

```txt
RECEIVED    주문 접수 대기
ACCEPTED    주문 접수
COOKING     조리 중
READY       조리 완료 / 결제 대기
COMPLETED   active 목록에서 제거 또는 결제 완료 표시 후 제거
CANCELED    취소 표시 후 제거
```

### 주방

구독:

```txt
orders:operations
```

수신 처리:

```txt
ORDER_LIST_CHANGED
-> queryClient.invalidateQueries(["kitchen-orders", "active"])
```

조회 대상:

```txt
RECEIVED
ACCEPTED
COOKING
```

`READY`, `COMPLETED`, `CANCELED`는 주방 active 보드에서 제외하거나 별도 완료/취소 영역에 짧게 보여준다.

### 직원

구독:

```txt
orders:operations
```

수신 처리:

```txt
ORDER_LIST_CHANGED
-> queryClient.invalidateQueries(["order-operations"])
```

조회 대상:

```txt
READY
```

직원 화면의 주요 업무:

```txt
조리 완료된 주문 확인
고객 응대/후불 결제
READY -> COMPLETED 처리
```

### 매니저/관리자

구독:

```txt
orders:operations
```

수신 처리:

```txt
ORDER_LIST_CHANGED
-> queryClient.invalidateQueries(["order-operations"])
```

조회 대상:

```txt
RECEIVED
ACCEPTED
COOKING
READY
COMPLETED
CANCELED
```

운영 모니터링 화면에서는 상태별 필터를 둔다.

## 7. 백엔드 구조

공통 WebSocket 인프라:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/websocket/AppWebSocketHandler.java
restaurant-book-server/src/main/java/com/cj/restaurantbook/websocket/WebSocketConfig.java
restaurant-book-server/src/main/java/com/cj/restaurantbook/websocket/JwtHandshakeInterceptor.java
restaurant-book-server/src/main/java/com/cj/restaurantbook/websocket/WsMessage.java
```

주문 이벤트 전파:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/order/application/OrderBroadcaster.java
```

서비스:

```txt
OrderService
- 고객 주문 생성/취소
- OrderBroadcaster 호출

KitchenOrderService
- 주방 상태 변경
- OrderBroadcaster 호출

OrderOperationService
- 직원/데스크 결제 완료
- OrderBroadcaster 호출
```

중요 원칙:

```txt
DB commit 이후에만 WebSocket 발행
```

구현 방식:

```txt
TransactionSynchronizationManager.registerSynchronization(...)
afterCommit()에서 broadcast
```

이유:

- 이벤트를 받은 화면이 즉시 REST refetch할 때 커밋 전 상태를 읽으면 안 된다.
- WebSocket은 상태 원본이 아니라 변경 신호다.
- 최종 상태는 DB와 REST API가 기준이다.

## 8. 프론트 구조

공통 WebSocket 훅:

```txt
restaurant-book-front/src/shared/hooks/useAppWebSocket.ts
```

주문 전파 훅:

```txt
restaurant-book-front/src/shared/hooks/useOperationalOrdersWebSocket.ts
restaurant-book-front/src/shared/hooks/useKitchenOrdersWebSocket.ts
restaurant-book-front/src/shared/hooks/useStaffOrdersWebSocket.ts
restaurant-book-front/src/shared/hooks/useCustomerOrdersWebSocket.ts
```

권장 책임:

```txt
useAppWebSocket
- 연결/재연결/heartbeat
- topic listener registry
- SUBSCRIBE/UNSUBSCRIBE

useOperationalOrdersWebSocket
- orders:operations 구독
- ORDER_LIST_CHANGED 수신
- 운영 주문 query invalidate

useKitchenOrdersWebSocket
- 주방 보드 query invalidate

useStaffOrdersWebSocket
- 직원 주문 query invalidate

useCustomerOrdersWebSocket(tableName)
- customer:orders/{tableName} 구독
- 고객 active 주문 query invalidate
```

## 9. 구현 우선순위

1. 주문 상태 enum 정리: `ACCEPTED` 추가, `READY -> COMPLETED` 의미를 결제 완료로 확정
2. 주방 REST API 구현
3. 직원/운영 REST API 구현
4. 주방 UI를 polling 기반으로 먼저 구현
5. 직원 주문 UI를 polling 기반으로 먼저 구현
6. WebSocket 공통 인프라 구현
7. `OrderBroadcaster` 구현
8. 고객/주방/직원 화면에 구독 훅 연결
9. polling 빈도 낮추고 WebSocket 이벤트 중심으로 전환

다음 세션에서는 아래 순서로 진행한다.

```txt
RestaurantBook 주방/직원 주문 상태 흐름을 구현해줘.

참고 문서:
- docs-for-필수 기능 개발/주방 페이지 구현계획/00-주방 페이지 단계별 파일별 구현 계획.md
- docs-for-필수 기능 개발/주방 페이지 구현계획/이벤트 생산 소비 관련.md

핵심 상태 흐름:
RECEIVED -> ACCEPTED -> COOKING -> READY -> COMPLETED

의미:
- READY는 조리 완료이자 후불 결제 대기
- COMPLETED는 직원/데스크가 결제 완료 처리한 주문 종료
- 서빙 완료 상태는 만들지 않는다

역할:
- ROLE_KITCHEN: RECEIVED -> ACCEPTED -> COOKING -> READY
- ROLE_STAFF: READY -> COMPLETED
- ROLE_MANAGER: 매장 관리자, 데스크로 바꾸지 않음
- ROLE_STAFF는 데스크/서빙 포함 현장 직원

먼저 REST API와 polling UI를 구현하고,
그 다음 BeautyBook의 공통 WebSocket pub/sub 패턴을 참고해서
OrderBroadcaster 기반 afterCommit 이벤트 전파를 붙여줘.

WebSocket MVP 이벤트:
- orders:operations / ORDER_LIST_CHANGED
- customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED

WebSocket은 전체 주문 payload를 밀지 말고 변경 신호만 보내고,
프론트는 React Query invalidate로 REST 재조회하게 해줘.
```
