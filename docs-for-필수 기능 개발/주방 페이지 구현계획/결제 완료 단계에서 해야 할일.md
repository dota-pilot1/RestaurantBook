# 결제 완료 단계에서 해야 할 일

## 현재 상태

직원 화면에는 `READY -> COMPLETED` 처리 버튼이 있다.

현재 `결제 완료` API는 주문 상태를 `COMPLETED`로 변경하는 역할만 한다.

- `Order READY -> COMPLETED`
- 주방/직원/고객 WebSocket 변경 신호 전파
- 고객 active 주문 목록에서는 `COMPLETED`가 제외되어 사라짐
- 별도 결제 정보는 아직 저장하지 않음

따라서 지금의 `COMPLETED`는 "결제 완료로 주문 종료"라는 상태 표현이고, 매출/정산의 근거가 되는 결제 도메인은 아직 없다.

## 1차 완료 범위

Payment 도메인 없이 주문 상태 완료와 실시간 전파를 먼저 마무리한다.

완료 기준:

- 직원이 `결제 완료` 클릭
- 주문 상태 `READY -> COMPLETED`
- `OrderBroadcaster` afterCommit으로 `COMPLETED` 변경 신호 전파
- 고객 active 주문 목록에서 해당 주문 제거
- 주방 보드는 `READY`까지만 조회하므로 해당 주문 제거
- 직원 보드에서는 `결제 완료` 컬럼으로 이동

이 범위는 현재 구현되어 있으며, 다음 단계에서는 Payment 저장과 매출 화면을 붙인다.

## 2차 목표

결제 완료 버튼을 누르면 주문 상태 변경과 결제 기록 생성을 하나의 트랜잭션으로 처리한다.

흐름:

1. 직원이 `READY` 주문에서 `결제 완료` 클릭
2. `Payment` 생성
3. 주문 상태를 `COMPLETED`로 변경
4. 주방/직원/고객 WebSocket 변경 신호 전파
5. 고객 키오스크 active 주문 목록에서 제거
6. 직원 보드에서는 `결제 완료` 컬럼으로 이동
7. 관리자 대시보드와 `/sales` 페이지는 `Payment` 기준으로 집계

## Payment 도메인 MVP

최소 필드:

```text
payments
- id
- order_id
- amount
- method
- status
- paid_at
- handled_by
- created_at
- updated_at
```

권장 enum:

```text
PaymentMethod
- CARD
- CASH
- ETC

PaymentStatus
- PAID
- CANCELED
- REFUNDED
```

MVP에서는 실제 PG 연동 없이 현장 결제 기록만 남긴다.

## API 변경

현재:

```text
PATCH /api/operations/orders/{orderId}/complete
```

개선:

```text
PATCH /api/operations/orders/{orderId}/complete
body:
{
  "paymentMethod": "CARD"
}
```

처리:

- 주문 상태가 `READY`인지 확인
- 이미 결제된 주문이면 중복 결제 방지
- `Payment` 생성
- 주문 `complete()`
- `OrderBroadcaster`로 `COMPLETED` 변경 신호 전파

## 프론트 변경

직원 화면:

- `결제 완료` 클릭 시 결제수단 선택
- 최소 선택지: `카드`, `현금`, `기타`
- 확인 후 API 호출
- 성공 시 보드 재조회

고객 화면:

- active 주문 조회는 현재처럼 `RECEIVED, ACCEPTED, COOKING, READY`만 노출
- 주문이 `COMPLETED` 되면 active 목록에서 사라짐
- 별도 완료 안내는 MVP에서는 필수 아님

주방 화면:

- 주방은 `READY`까지만 관리
- 직원 결제 완료 후 주방 보드에는 영향 없음

## 주문 삭제/비활성화 기준

주문 삭제는 하지 않는다.

운영 화면 노출 여부는 주문 상태로 판단한다.

```text
활성 주문:
- RECEIVED
- ACCEPTED
- COOKING
- READY

비활성 주문:
- COMPLETED
- CANCELED
```

`COMPLETED` 주문은 매출/정산/클레임 확인을 위해 보관한다.

주문 관리 페이지는 추후 별도로 만든다.

- 기간별 조회
- 상태별 조회
- 테이블별 조회
- 결제수단/금액 확인
- 취소 사유 확인

## 관리자 대시보드

매출은 직원/주방 화면이 아니라 관리자 화면에서 본다.

관리자 대시보드의 `오늘 매출` 카드는 요약 지표로 유지한다.

- 오늘 결제 완료 금액
- 전일 대비 증감은 추후 구현 가능
- 카드 클릭 또는 우측 아이콘 클릭 시 `/sales` 페이지로 이동

대시보드 카드에서는 상세 다이어로그보다 페이지 이동이 적절하다.

이유:

- 매출은 기간 필터, 결제수단, 취소/환불, 주문 상세까지 확장될 가능성이 큼
- 다이어로그는 빠른 미리보기에는 좋지만 정산/검토 화면으로는 좁음
- `/sales`를 상세 페이지로 두면 관리자 메뉴 구조와도 맞음

## 매출 페이지

현재 `/sales`는 실질 구현 전 placeholder에 가깝다.

2차 범위에서는 `/sales`를 Payment 기반 상세 조회 페이지로 구현한다.

MVP 화면 구성:

- 오늘/이번 주/이번 달/기간 직접 선택 필터
- 총 매출
- 결제 건수
- 결제수단별 매출: 카드, 현금, 기타
- 최근 결제 목록
- 주문번호, 테이블, 결제수단, 금액, 결제시각
- 취소/환불 영역은 placeholder 또는 0원 표시

초기에는 차트보다 표와 요약 카드 중심으로 구현한다.

우선순위:

1. `Payment` 테이블에 결제 기록 저장
2. `결제 완료` API에서 `Payment` 생성 + `Order COMPLETED` 처리
3. 관리자 대시보드 `오늘 매출`을 Payment 합계로 교체
4. `/sales`에서 Payment 기준 집계 구현
5. 직원/주방/고객 화면에서 완료 주문이 자연스럽게 사라지거나 이동하는지 재확인
