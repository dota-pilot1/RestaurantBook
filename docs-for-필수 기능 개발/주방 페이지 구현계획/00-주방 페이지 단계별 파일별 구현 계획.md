# 주방 페이지 단계별 파일별 구현 계획

## 0. 결론

주문 생성 직후 상태와 주방이 실제로 접수한 상태를 분리한다.

```txt
RECEIVED       고객 주문 생성 완료, 주방 접수 대기
ACCEPTED       주방이 주문 접수
COOKING        조리 시작
READY          조리 완료, 후불 결제 대기
COMPLETED      후불 결제 완료, 주문 종료
CANCELED       취소
```

현재 코드는 주문 생성 시 `RECEIVED`를 저장하고 고객 화면에서 `주문 접수 대기`로 표시한다. 그래서 주방 화면에서 상태를 두 번 바꾸려면 `ACCEPTED`를 추가하는 편이 맞다.

```txt
고객 주문 생성 -> RECEIVED
주방 주문 접수 버튼 -> ACCEPTED
주방 조리 시작 버튼 -> COOKING
주방 조리 완료 버튼 -> READY
데스크/직원 결제 완료 버튼 -> COMPLETED
```

실시간 전파는 `/Users/terecal/beauty-book-hair`의 WebSocket 구조를 참고한다. 특히 다음 패턴을 그대로 가져온다.

- 서버: `topicSessions` 기반 pub/sub
- 서버: 서비스 트랜잭션 반영 후 `broadcast`
- 프론트: 전역 WebSocket manager + `useAppWebSocketTopic`
- 프론트: 수신 이벤트에서 React Query 캐시 invalidate 또는 직접 patch

초기 구현 순서는 `주방 UI + REST polling -> 상태 변경 API -> WebSocket 전파`가 좋다. 이렇게 하면 WebSocket이 늦어져도 주방 페이지가 먼저 동작한다.

주방 UI는 현재 목업처럼 4컬럼 보드가 정석에 가깝다.

```txt
접수 대기 -> 접수됨 -> 조리중 -> 조리 완료
```

주방은 `READY`까지만 만든다. `READY` 이후에는 직원/데스크 화면에서 결제 완료 처리로 `COMPLETED`가 된다. `서빙 완료`, `픽업 완료`, `결제 상태 세분화`는 MVP에 넣지 않는다.

## 0-1. BeautyBook 관리자 채팅 상태 전파 분석

BeautyBook의 관리자 채팅 인박스는 공통 WebSocket pub/sub 구조다.

참고 파일:

- `/Users/terecal/beauty-book-hair/beauty-book-server/src/main/java/com/cj/beautybook/websocket/AppWebSocketHandler.java`
- `/Users/terecal/beauty-book-hair/beauty-book-server/src/main/java/com/cj/beautybook/consultation/application/ConsultationRoomService.java`
- `/Users/terecal/beauty-book-hair/beauty-book-server/src/main/java/com/cj/beautybook/consultation/application/ConsultationMessageService.java`
- `/Users/terecal/beauty-book-hair/beauty-book--front/src/shared/hooks/useAppWebSocket.ts`
- `/Users/terecal/beauty-book-hair/beauty-book--front/src/shared/hooks/useConsultationWebSocket.ts`
- `/Users/terecal/beauty-book-hair/beauty-book--front/src/features/consultation/ConsultationInbox.tsx`
- `/Users/terecal/beauty-book-hair/beauty-book--front/src/widgets/floating-chat/model/useRecentChatActivity.ts`
- `/Users/terecal/beauty-book-hair/개발 히스토리/채팅방 채널 구독 수정 문제 해결/공통 WebSocket 구독 관리 원칙.md`

관리자 채팅 인박스의 핵심 구조:

```txt
프론트 useConsultationRoomsWebSocket
  -> topic "consultations:list" SUBSCRIBE

서버 AppWebSocketHandler
  -> topicSessions["consultations:list"] 에 세션 저장

상담방 생성/재개/상태 변경/삭제/고객 메시지
  -> ConsultationRoomService 또는 ConsultationMessageService
  -> webSocketHandler.broadcastRoomListChanged(...)
  -> WsMessage("ROOM_LIST_CHANGED", "consultations:list", payload)

프론트 수신
  -> queryClient.invalidateQueries({ queryKey: ["consultations"], exact: false })
  -> REST API로 DB 기준 목록 재조회
```

중요한 점은 WebSocket payload로 전체 목록을 밀어주지 않는다는 것이다. WebSocket은 “변경 발생 신호”만 보내고, 화면은 React Query invalidate로 서버 상태를 다시 읽는다. 주문 상태 전파도 이 방식이 맞다.

관리자 채팅에서 주문에 가져올 수 있는 패턴:

- `consultations:list` 같은 글로벌 운영 토픽을 둔다.
- 이벤트명은 목록 변경 신호로 단순화한다.
- payload는 `reason`, `id`, 필요 최소 메타만 담는다.
- 수신자는 캐시를 invalidate해서 DB 기준으로 다시 맞춘다.
- 특정 화면이 이미 상세 데이터를 보고 있으면 `ROOM_UPDATE`처럼 캐시 patch를 추가할 수 있다.
- 여러 화면에 같은 신호가 필요하면 fan-out 메서드를 서비스에 둔다.

주문에 적용할 매핑:

```txt
BeautyBook consultations:list       -> RestaurantBook orders:operations
BeautyBook ROOM_LIST_CHANGED        -> RestaurantBook ORDER_LIST_CHANGED
BeautyBook NEW_CUSTOMER_MESSAGE     -> RestaurantBook NEW_ORDER_RECEIVED
BeautyBook consultations:user/{id}  -> RestaurantBook customer:orders/{tableName}
BeautyBook ROOM_UPDATE              -> RestaurantBook ORDER_STATUS_CHANGED
```

주문 상태 전파에서 권장하는 이벤트 구분:

```txt
ORDER_LIST_CHANGED
- 운영 화면 목록 재조회 신호
- 주방, 직원, 데스크, 매니저 주문 화면이 공통으로 수신
- 주문 생성, 접수, 조리 시작, 조리 완료, 결제 완료, 취소 때 발행

NEW_ORDER_RECEIVED
- 새 주문 사운드/배지용 신호
- 주문 생성 때만 발행

CUSTOMER_ORDERS_CHANGED
- 고객 테이블 주문 내역 재조회 신호
- 해당 tableName 토픽에만 발행

ORDER_STATUS_CHANGED
- 선택 사항
- orderId, status 정도를 담아 고객/주방/직원 캐시 patch에 사용 가능
```

초기에는 `ORDER_LIST_CHANGED`, `CUSTOMER_ORDERS_CHANGED`만 구현해도 충분하다. `NEW_ORDER_RECEIVED`는 사운드/배지 UX를 붙일 때 추가하고, `ORDER_STATUS_CHANGED`는 깜빡임 없이 카드 위치를 즉시 바꾸고 싶을 때 추가한다.

주의할 점:

- BeautyBook 상담방 일부 broadcast는 트랜잭션 안에서 바로 호출된다. 주문은 주방/고객 화면 정합성이 더 중요하므로 `OrderBroadcaster.broadcastAfterCommit(...)`로 커밋 후 발행을 기본으로 한다.
- `customer:orders/{tableName}`은 MVP에서는 테이블명 기반이지만, 장기적으로는 테이블 세션 토큰 또는 주문 세션 키가 필요하다.
- `orders:operations`는 반드시 `ROLE_ADMIN`, `ROLE_MANAGER`, `ROLE_KITCHEN`, `ROLE_STAFF`만 구독 가능하게 막는다.
- 단일 주방 토픽은 채널 전환 문제가 거의 없지만, 고객 토픽처럼 동적으로 바뀌는 토픽은 BeautyBook의 “서버가 같은 계열 이전 topic을 정리” 원칙을 적용한다.

## 0-2. 아키텍처 판단

BeautyBook 방식은 교과서적인 WebSocket pub/sub라고 볼 수 있다. 더 정확히는 “WebSocket event notification + REST state sync” 패턴이다.

```txt
Write API
  -> DB 상태 변경
  -> commit
  -> WebSocket으로 변경 신호 발행
  -> 구독 화면은 REST query invalidate/refetch
```

이 방식이 주방 주문 보드에 적합한 이유:

- 주문 목록은 화면마다 필요한 필터와 정렬이 다를 수 있다.
- WebSocket payload로 전체 주문 목록을 보내면 서버와 프론트 캐시 정합성 관리가 복잡해진다.
- 이벤트 누락, 재연결, 브라우저 sleep 후 복귀 같은 상황에서도 REST 재조회가 최종 정합성을 보장한다.
- 주방 보드는 초 단위 실시간성이면 충분하고, 밀리초 단위 스트리밍이 필요한 도메인이 아니다.
- 기존 React Query 구조와 잘 맞는다.

대안과 비교:

```txt
1. WebSocket payload에 전체 주문/상태를 담아 직접 patch
   장점: 즉시 반응, REST 재조회 감소
   단점: 이벤트 순서/중복/누락/재연결 처리가 어려움
   판단: 주문 보드 MVP에는 과함

2. WebSocket은 변경 신호만 보내고 REST 재조회
   장점: 단순함, 정합성 강함, 구현/디버깅 쉬움
   단점: 이벤트마다 API 호출 발생
   판단: 현재 RestaurantBook에 가장 적합

3. polling만 사용
   장점: 가장 단순함
   단점: 새 주문 반응이 늦거나 polling 비용 증가
   판단: 1차 UI 검증용으로 좋고, 최종 UX는 WebSocket 보완 필요

4. SSE
   장점: 서버 -> 클라이언트 단방향 알림에는 단순
   단점: 이미 BeautyBook 공통 WS 패턴이 있고 양방향 subscribe/unsubscribe가 필요
   판단: 새 기술을 섞을 이유가 적음
```

공통 로직으로 둘 범위:

```txt
공통화 권장
- WebSocket 연결/재연결/heartbeat
- SUBSCRIBE/UNSUBSCRIBE envelope
- topic -> listener registry
- token query param handshake
- 서버 topicSessions 등록/해제/broadcast 유틸
- WsMessage envelope(type, topic, data)
- afterCommit broadcaster helper

도메인별 분리 권장
- topic 이름
- 이벤트 이름
- 구독 권한
- payload 구조
- 어떤 queryKey를 invalidate할지
- 상태 전이 검증
- 고객/주방/관리자 fan-out 정책
```

즉, 공통 로직은 “메시지를 안전하게 보내고 받는 인프라”까지만 두고, “이 이벤트가 무슨 의미인지”는 주문 도메인에 남기는 편이 맞다.

RestaurantBook에 적용할 구조:

```txt
shared websocket infra
- websocket/AppWebSocketHandler
- websocket/WebSocketConfig
- websocket/JwtHandshakeInterceptor
- websocket/WsMessage
- front shared/hooks/useAppWebSocket.ts

order/kitchen domain realtime
- order/application/OrderBroadcaster.java
- kitchen/application/KitchenOrderService.java
- front shared/hooks/useOperationalOrdersWebSocket.ts
- front shared/hooks/useKitchenOrdersWebSocket.ts
- front shared/hooks/useStaffOrdersWebSocket.ts
- front shared/hooks/useCustomerOrdersWebSocket.ts
```

권장 설계:

- `AppWebSocketHandler`는 특정 도메인 비즈니스 로직을 모르게 한다.
- `OrderBroadcaster`가 `orders:operations`, `customer:orders/{tableName}` 같은 주문 토픽 이름을 소유한다.
- `KitchenOrderService`는 상태 전이와 저장만 담당하고, 저장 성공 후 `OrderBroadcaster`에 전파를 위임한다.
- `OrderBroadcaster`는 `afterCommit`으로만 발행한다.
- 프론트 `useAppWebSocket.ts`는 완전 공통이다.
- 프론트 `useOperationalOrdersWebSocket.ts`는 운영 주문 query key만 알고 invalidate한다.
- `useKitchenOrdersWebSocket`, `useStaffOrdersWebSocket`은 공통 운영 훅을 감싸서 각 화면 query key를 맞춘다.

최종 판단:

```txt
채택: BeautyBook의 공통 WebSocket pub/sub 인프라 패턴
보완: 주문은 반드시 afterCommit broadcast
공통화: transport/envelope/subscribe 관리까지만
분리: 주문 이벤트, 토픽, 권한, query invalidation
초기 전략: polling 동작 보장 후 WebSocket 신호 기반으로 전환
```

## 0-3. 주문 상태 전파 대상과 토픽 설계

주문 상태는 주방만의 데이터가 아니다. 같은 주문 변경 이벤트를 다음 화면들이 받아야 한다.

```txt
고객 키오스크
- 자기 테이블의 주문 상태 확인
- RECEIVED, ACCEPTED, COOKING, READY, CANCELED 반영
- 주문 취소 가능 여부 갱신

주방
- 신규 주문 수신
- RECEIVED -> ACCEPTED -> COOKING -> READY 변경 실행
- 취소된 주문 즉시 제거 또는 취소 표시

직원/데스크/서빙
- READY 주문 확인
- 테이블별 제공/픽업 대기 확인
- READY -> COMPLETED 후불 결제 완료 처리
- 후불 미결제 테이블 확인

매니저/관리자
- 전체 주문 모니터링
- 취소/오류 대응
- 운영 통계/주문 이력 확인
```

따라서 토픽은 “주방 전용”이 아니라 “운영 공통”과 “고객 스코프”로 나누는 편이 맞다.

권장 토픽:

```txt
orders:operations
- 구독자: ROLE_ADMIN, ROLE_MANAGER, ROLE_KITCHEN, ROLE_STAFF
- 용도: 주방, 직원, 데스크, 매니저 화면의 주문 목록 변경 신호
- 이벤트: ORDER_LIST_CHANGED, NEW_ORDER_RECEIVED, ORDER_STATUS_CHANGED

customer:orders/{tableName}
- 구독자: 해당 테이블 고객 화면
- 용도: 고객 키오스크의 active 주문 상태 변경 신호
- 이벤트: CUSTOMER_ORDERS_CHANGED, ORDER_STATUS_CHANGED

orders:table/{tableName}
- 선택 후보
- 구독자: 직원/데스크가 특정 테이블 상세를 열었을 때
- MVP에서는 `orders:operations` + REST 상세 재조회로 충분하므로 보류
```

fan-out 규칙:

```txt
주문 생성
-> orders:operations / ORDER_LIST_CHANGED
-> orders:operations / NEW_ORDER_RECEIVED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED

주방 주문 접수 RECEIVED -> ACCEPTED
-> orders:operations / ORDER_LIST_CHANGED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
-> 선택: 양쪽에 ORDER_STATUS_CHANGED

조리 시작 ACCEPTED -> COOKING
-> orders:operations / ORDER_LIST_CHANGED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
-> 선택: 양쪽에 ORDER_STATUS_CHANGED

조리 완료 COOKING -> READY
-> orders:operations / ORDER_LIST_CHANGED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
-> 직원/데스크 화면은 READY 주문 목록을 refetch

결제 완료 READY -> COMPLETED
-> orders:operations / ORDER_LIST_CHANGED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
-> 고객 active 주문에서 제거하거나 결제 완료 표시

취소 RECEIVED/ACCEPTED 가능 후보 -> CANCELED
-> orders:operations / ORDER_LIST_CHANGED
-> customer:orders/{tableName} / CUSTOMER_ORDERS_CHANGED
```

이벤트 payload는 최소로 둔다.

```json
{
  "reason": "STATUS_CHANGED",
  "orderId": 123,
  "orderNo": "20260507222210-5163",
  "tableName": "3번 테이블",
  "fromStatus": "ACCEPTED",
  "toStatus": "COOKING"
}
```

payload에 전체 주문 상세를 넣지 않는 이유:

- 주방, 직원, 고객 화면의 목록 조건이 다르다.
- 주문 카드의 표시 필드가 늘어날수록 WebSocket payload 버전 관리가 번거롭다.
- refetch 방식이면 이벤트 순서가 조금 섞여도 최종 DB 상태로 수렴한다.

프론트 훅 설계:

```txt
useOperationalOrdersWebSocket
- orders:operations 구독
- ORDER_LIST_CHANGED 수신 시 운영 주문 query invalidate
- NEW_ORDER_RECEIVED 수신 시 사운드/배지 선택 처리
- ROLE_STAFF, ROLE_KITCHEN, ROLE_MANAGER 화면에서 재사용

useKitchenOrdersWebSocket
- useOperationalOrdersWebSocket을 감싸거나 동일 토픽 구독
- ["kitchen-orders", "active"] invalidate

useStaffOrdersWebSocket
- useOperationalOrdersWebSocket을 감싸거나 동일 토픽 구독
- ["staff-orders", "ready"] 또는 ["orders", "operations"] invalidate

useCustomerOrdersWebSocket(tableName)
- customer:orders/{tableName} 구독
- ["customer-active-orders", tableName] invalidate
```

백엔드 서비스 책임:

```txt
OrderService
- 고객 주문 생성/취소
- 저장 후 OrderBroadcaster 호출

KitchenOrderService
- RECEIVED -> ACCEPTED
- ACCEPTED -> COOKING
- COOKING -> READY
- 저장 후 OrderBroadcaster 호출

StaffOrderService 또는 OrderOperationService
- READY -> COMPLETED
- 데스크/서빙/직원용 주문 조회
- 저장 후 OrderBroadcaster 호출

OrderBroadcaster
- orders:operations fan-out
- customer:orders/{tableName} fan-out
- afterCommit 발행 보장
```

정리하면 `주문 상태 전파`는 도메인 이름을 `kitchen realtime`으로 잡지 말고 `order realtime`으로 잡아야 한다. 주방은 주문 상태를 변경하는 주요 생산자이자 소비자이고, 고객/직원/데스크는 같은 주문 이벤트를 자기 화면 기준으로 소비한다.

## 0-4. 역할 이름 판단: 매니저 vs 데스크

현재 기본 역할:

```txt
ROLE_ADMIN     관리자
ROLE_MANAGER   매니저
ROLE_KITCHEN   주방
ROLE_STAFF     직원
ROLE_CUSTOMER  고객
```

`매니저`를 `데스크`로 바꾸는 것은 권장하지 않는다. 매니저는 매장 운영 관리자이고, 데스크는 현장 업무 포지션에 가깝다. 둘은 권한 범위가 다르다.

권장 해석:

```txt
ROLE_MANAGER
- 매장 운영 관리자
- 주문 모니터링
- 취소/예외 처리
- 직원/주방 업무 확인
- 관리자보다는 좁고 직원보다는 넓은 권한

ROLE_STAFF
- 직원, 데스크, 서빙 포지션을 포함하는 MVP 운영 역할
- READY 주문 확인
- 후불 결제 완료 처리: READY -> COMPLETED
- 테이블별 미결제 주문 확인
```

따라서 MVP에서는 별도 `ROLE_DESK`를 만들지 않는다. 데스크 업무는 `ROLE_STAFF`가 처리한다. UI 문구만 필요하면 `직원` 버튼을 `직원/데스크` 또는 `데스크`로 보여줄 수 있지만, 내부 role code는 `ROLE_STAFF`를 유지한다.

별도 `ROLE_DESK`가 필요한 시점:

- 서빙 직원은 결제 완료를 누르면 안 된다.
- 데스크 직원만 결제/환불/영수증 권한을 가져야 한다.
- 직원 근무 포지션별 대시보드가 확실히 달라진다.
- 감사 로그에서 결제 처리자를 데스크 권한으로 따로 구분해야 한다.

지금 단계에서는 역할을 늘리면 권한/테스트 계정/라우팅/시드/권한 관리가 같이 늘어난다. 그래서 `ROLE_STAFF = 데스크/서빙 포함 현장 직원`으로 시작하고, 결제 도메인이 커질 때 `ROLE_DESK` 분리를 검토한다.

- 주방 탭에서 `주문 접수` 클릭하면 고객 탭 상태가 `주문 접수`로 변경
- 주방 탭에서 `조리 시작` 클릭하면 고객 탭 상태가 `조리 중`으로 변경
- 주방 탭에서 `조리 완료` 클릭하면 직원/데스크 화면에 `결제 대기` 주문으로 표시
- 직원/데스크 화면에서 `결제 완료` 처리하면 고객 탭 active 주문에서 제거 또는 완료 표시

## 8. 7단계: 운영 UX 보완

후속 후보:

- 새 주문 사운드 on/off
- 새 주문 카드 강조 애니메이션
- 경과 시간 색상:
  - 0~5분 일반
  - 5~10분 주의
  - 10분 이상 지연
- 주문 유형 필터:
  - 전체
  - 매장
  - 포장
- 완료 주문 접기
- 직원/데스크 화면에서 `READY -> COMPLETED` 결제 완료 처리
- 주문 상태 이력 테이블 추가

후속에서도 신중할 것:

- `서빙 완료`: 서빙 직원의 버튼 클릭 업무가 늘어나므로 기본 상태로 두지 않는다.
- `픽업 완료`: 포장 주문량이 많아지고 픽업 추적이 필요할 때만 검토한다.
- `PAID` 별도 상태: 결제 수단, 환불, 영수증, 부분 결제 도메인이 생길 때 검토한다. MVP에서는 `COMPLETED`가 결제 완료와 주문 종료를 함께 의미한다.
- 주방에서 결제 완료: 역할 경계가 흐려지므로 직원/데스크 화면에서 처리한다.

## 9. 테스트 계획

백엔드:

```txt
./gradlew test
```

테스트 후보:

- `RECEIVED -> ACCEPTED` 성공
- `RECEIVED -> COOKING` 직접 전이 실패
- `ACCEPTED -> COOKING` 성공
- `COOKING -> READY` 성공
- `READY -> COMPLETED` 성공
- `ACCEPTED -> COMPLETED` 직접 전이 실패
- `CANCELED -> ACCEPTED` 실패
- 주방 active 조회가 `RECEIVED`, `ACCEPTED`, `COOKING`만 반환
- 직원/데스크 ready 조회가 `READY` 주문을 반환
- 상태 변경 후 `orders:operations`와 `customer:orders:{tableName}` 전파가 afterCommit으로 예약됨

프론트:

```txt
npm run build
```

수동 시나리오:

1. 고객 `/customer`에서 3번 테이블 주문 생성
2. 주방 `/kitchen`에서 `접수 대기` 컬럼에 주문 노출 확인

4. 고객 화면 주문 상태가 `주문 접수`로 변경되는지 확인
5. `조리 시작` 클릭 후 `조리중` 컬럼 이동 확인
6. 고객 화면 주문 상태가 `조리 중`으로 변경되는지 확인
