# 웹소켓 토큰 만료 문제 관련 정리

## 상황

주방/직원/고객 주문 상태 변경은 REST 재조회와 WebSocket 변경 신호를 함께 사용한다.

- REST API: 실제 주문 데이터 조회/상태 변경
- WebSocket: `ORDER_LIST_CHANGED`, `CUSTOMER_ORDERS_CHANGED` 같은 변경 신호만 전파
- 프론트: WebSocket 신호 수신 후 React Query invalidate로 REST 재조회

이때 브라우저에 남아 있는 access token이 만료된 상태로 `/ws/app`에 연결하면 WebSocket 핸드셰이크가 실패할 수 있다.

## 원인

WebSocket은 일반 REST 요청과 별도 연결이다.

REST 요청은 API 호출 시점마다 토큰 갱신/재시도를 처리하기 쉽지만, WebSocket은 최초 연결 URL에 포함된 token이 만료되어 있으면 연결 자체가 열리지 않는다.

대표 증상:

- 브라우저 콘솔에 `WebSocket connection to ws://.../ws/app?... failed`
- 주문 조회/버튼 동작은 되는 것처럼 보이는데 실시간 전파만 안 됨
- 새로고침 또는 재로그인 후 정상화되는 경우가 있음

## 권한 정책

WebSocket을 전부 익명 허용하지 않는다.

- 운영 주제: `orders:operations`
  - 주방/직원/관리자 화면에서 사용
  - `ROLE_KITCHEN`, `ROLE_STAFF`, `ROLE_MANAGER`, `ROLE_ADMIN` 등 권한 확인 필요
- 고객 주제: `customer:orders/{tableName}`
  - 고객 태블릿에서 사용
  - 테이블 단위 변경 신호만 받으므로 MVP에서는 익명 구독 허용 가능

운영 WebSocket까지 토큰 검증을 빼면 REST 권한 모델과 실시간 권한 모델이 어긋난다.

## 처리 방향

운영 WebSocket은 access token을 계속 사용하되, 연결 실패 시 refresh token으로 access token을 재발급받고 재연결한다.

흐름:

1. WebSocket 연결 시 현재 access token을 붙인다.
2. 연결이 열리기 전에 종료되면 토큰 만료 가능성으로 본다.
3. refresh token으로 access token을 재발급한다.
4. 새 access token으로 WebSocket을 다시 연결한다.
5. 로그인/토큰 변경 이벤트가 발생하면 기존 WebSocket도 새 토큰 기준으로 재연결한다.

## UX 기준

실시간 연결 실패가 주문 상태 흐름 자체를 막으면 안 된다.

- 버튼 클릭/상태 변경은 REST API 기준으로 처리
- WebSocket은 변경 신호 전파용
- WebSocket이 끊겨도 수동 새로고침 또는 polling/재조회로 복구 가능해야 함
- 토큰 만료는 사용자에게 에러로 노출하기보다 내부적으로 refresh 후 재연결하는 것이 자연스러움

## 결론

현재 방향은 다음이 적절하다.

- 고객 WebSocket: 테이블 주제만 익명 허용
- 운영 WebSocket: 권한 검증 유지
- access token 만료: refresh token으로 재발급 후 WebSocket 재연결
- payload: 전체 주문 데이터가 아니라 변경 신호만 전파
- 데이터 정합성: React Query invalidate 후 REST 재조회로 확보
