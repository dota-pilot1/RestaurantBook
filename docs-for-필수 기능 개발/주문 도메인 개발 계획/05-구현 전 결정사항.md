# 주문 도메인 구현 전 결정사항

## 1. API 이름

권장:

```txt
POST /api/customer/orders
```

이유:

- 고객 키오스크에서 호출하는 주문 생성 API다.
- 관리자 주문 관리 API `/api/orders`와 권한 경계를 분리할 수 있다.
- 현재 고객 상품 조회 API `/api/customer/sale-products`와 일관적이다.

## 2. 결제하기 vs 주문 접수하기

현재 버튼:

```txt
결제하기
```

주문 도메인 MVP는 실제 결제가 없으므로 권장 문구:

```txt
주문 접수하기
```

결제 도메인 연동 이후:

```txt
결제하기
```

## 3. 주문 상태 초기값

권장:

```txt
RECEIVED
```

이유:

- 고객이 주문을 제출했고 매장 시스템에 접수된 상태를 명확히 표현한다.
- 후속 주방 보드에서 `COOKING`, `READY`, `COMPLETED`로 자연스럽게 확장된다.

비권장:

```txt
PENDING
```

이유:

- 결제 대기인지, 주방 접수 대기인지 의미가 모호하다.

## 4. 주문 번호

MVP 권장:

```txt
yyyyMMddHHmmss-random4
```

예:

```txt
20260507173122-4821
```

후속 권장:

```txt
일자별 A001, A002
```

후속 번호는 동시성 처리가 필요하므로 MVP에서는 단순한 고유 번호를 사용한다.

## 5. 같은 상품 중복 요청

프론트 장바구니는 이미 `type + id` 기준으로 합쳐져 있다.

그래도 API는 방어적으로 처리한다.

권장:

```txt
서버에서 type + id 기준으로 수량 합산
```

이유:

- 클라이언트 버그나 외부 호출에도 안정적이다.
- 사용자에게 의미 없는 400 에러를 줄일 수 있다.

## 6. 세트 구성 수량 저장 방식

권장:

```txt
order_item.quantity = 세트 주문 수량
order_item_component.quantity = 세트 1개 기준 구성 수량
```

예:

```txt
대표 한상 세트 x2
구성: 육회 비빔밥 x1, 오늘의 반찬 x1, 식혜 x1
```

실제 총 구성 수량:

```txt
order_item.quantity * order_item_component.quantity
```

이 방식이 세트 정의를 읽기 쉽고 주문 상세 표시도 자연스럽다.

## 7. 가격 신뢰

결정:

```txt
프론트 가격은 절대 저장에 사용하지 않는다.
```

서버가 저장할 값:

- `itemName`
- `unitPrice`
- `lineTotal`
- `totalAmount`
- 세트 구성 `componentName`

모두 DB에서 재조회한 값을 기준으로 한다.

## 8. 비로그인 주문

MVP 결정:

```txt
고객 주문 생성은 비로그인 허용
```

이유:

- 현재 고객 키오스크 페이지가 비로그인 접근을 전제로 한다.
- 현장 키오스크 주문은 계정 없이도 가능해야 한다.

후속:

- 온라인 고객 주문은 `user_id` 연결
- 키오스크 주문은 `source = KIOSK` 같은 필드 추가 가능

## 9. 주문 출처

MVP에서는 생략한다.

후속 후보:

```txt
source = KIOSK | STAFF | ONLINE
```

현재는 고객 키오스크 주문만 저장하므로 과한 필드다.

## 10. 주문/결제 분리

결정:

```txt
주문 도메인 먼저 저장
결제 도메인은 후속 분리
```

이유:

- 주문 저장 없이 결제를 붙이면 실패/취소/재시도 흐름이 복잡해진다.
- MVP에서는 주문 접수와 주방 흐름 검증이 먼저다.

후속 결제 도메인:

```txt
payments
payment_transactions
refunds
```
