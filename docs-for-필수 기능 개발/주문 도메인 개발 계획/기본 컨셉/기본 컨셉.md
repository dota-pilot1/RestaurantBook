장바구니에 담기
-> 주문 접수하기 클릭
-> 서버에 type/id/quantity 전송
-> 서버가 가격/이름/구성 재조회
-> orders / order_items / order_item_components 저장
-> 성공 응답
-> 장바구니 비우기


주의할점: 
주문 상태로 저장하는건 맞는데 현재 주문이 가능한 상황인지 검증 로직도 필요하다 이거지?
기준은 뭘로 해야 되는데?


답:
맞다. 주문 저장은 단순 insert가 아니라 "지금 이 상품을 이 주문 유형으로 주문할 수 있는가"를 서버에서 다시 검증한 뒤 저장해야 한다.

프론트 장바구니는 신뢰하지 않는다.
프론트는 사용자가 담아둔 의사 표현일 뿐이고, 주문 접수 시점에는 메뉴 상태가 바뀌었을 수 있다.

정리하면:

```txt
프론트 검증 = 고객 UX용
백엔드 검증 = 데이터 정합성용 필수 기준
```

프론트에서 이미 품절 버튼을 disabled 하고, 주문 불가 상품을 안 보여줘도 백엔드는 반드시 같은 기준을 다시 확인한다.

이유:

```txt
API 직접 호출 가능
키오스크 화면이 오래 열려 있을 수 있음
주문 직전 관리자가 상품 상태를 바꿀 수 있음
프론트 버그나 캐시 데이터가 있을 수 있음
```

즉 프론트 필터는 편의 기능이고, 실제 주문 가능 여부의 최종 판정은 백엔드가 한다.

기준은 고객 상품 조회 조건과 거의 같지만, 주문 저장은 더 엄격하다.

키오스크 식당 메뉴는 반찬 쇼핑몰처럼 실재고 수량을 관리하지 않는다.
현재 단계에서는 재고 계산이 아니라 판매 상태만 본다.

기준 정보는 상품 데이터다.

```txt
sale_menus.visible
sale_menus.status
sale_menus.available_dine_in
sale_menus.available_takeout

sale_menu_sets.visible
sale_menu_sets.status
sale_menu_sets.available_dine_in
sale_menu_sets.available_takeout
```

반찬 쇼핑몰은 후속으로 재고 수량/예약/차감 로직이 필요할 수 있지만, 키오스크 식당 메뉴 MVP에서는 과하다.

고객 화면 노출 가능:

```txt
visible = true
status in (ACTIVE, SOLD_OUT)
주문 유형 가능 여부 true
```

주문 저장 가능:

```txt
visible = true
status = ACTIVE
주문 유형 가능 여부 true
상품이 실제로 존재함
quantity >= 1
```

즉 `SOLD_OUT`은 고객 화면에 보여줄 수는 있지만 주문 저장은 절대 허용하지 않는다.

품절 상품 노출 정책:

```txt
키오스크에서는 SOLD_OUT을 보여주고 추가 버튼 disabled 하는 정책을 유지한다.
```

이유:

```txt
원래 파는 메뉴인데 지금 품절이라는 정보를 전달할 수 있다.
고객이 직원에게 메뉴 유무를 묻는 상황을 줄일 수 있다.
```

다만 화면이 복잡해지면 후속으로 `ACTIVE`만 노출하는 정책으로 바꿀 수 있다.
어느 쪽이든 주문 저장 기준은 항상 `status = ACTIVE`다.

## 단품 SALE_MENU 검증 기준

대상 테이블:

```txt
sale_menus
```

검증:

```txt
id로 sale_menus 조회 성공
visible = true
status = ACTIVE
orderType = DINE_IN 이면 availableDineIn = true
orderType = TAKEOUT 이면 availableTakeout = true
quantity >= 1
```

하나라도 실패하면 주문 전체를 저장하지 않는다.

## 세트 SALE_MENU_SET 검증 기준

대상 테이블:

```txt
sale_menu_sets
sale_menu_set_items
```

검증:

```txt
id로 sale_menu_sets 조회 성공
visible = true
status = ACTIVE
orderType = DINE_IN 이면 availableDineIn = true
orderType = TAKEOUT 이면 availableTakeout = true
세트 구성 item이 1개 이상 존재
quantity >= 1
```

세트 구성 안의 단품까지 주문 가능 상태인지도 체크할지 결정이 필요하다.

MVP 권장:

```txt
세트 자체의 visible/status/available만 주문 가능 기준으로 본다.
구성 단품의 현재 status는 주문 가능 여부에 직접 반영하지 않는다.
```

이유:

```txt
세트는 독립 판매 상품이다.
세트 구성 단품이 고객에게 별도 판매 중지 상태여도 세트 구성으로는 제공할 수 있다.
세트 판매 가능 여부는 관리자가 sale_menu_sets.status로 통제하는 것이 더 명확하다.
```

다만 구성 단품이 삭제되었거나 참조가 깨진 경우는 서버 오류/데이터 무결성 문제이므로 주문 저장을 막는다.

후속 재고 연동 단계에서는 구성 단품 재고까지 검증할 수 있다.

## 서버가 다시 계산해야 하는 값

프론트에서 보내면 안 되는 값:

```txt
상품명
가격
라인 합계
총액
세트 구성
```

서버가 DB에서 재조회해서 저장해야 하는 값:

```txt
order_items.item_name
order_items.unit_price
order_items.line_total
orders.total_amount
order_item_components.component_name
order_item_components.quantity
order_item_components.display_order
```

프론트 요청은 이것만 받는다.

```json
{
  "orderType": "DINE_IN",
  "items": [
    {
      "type": "SALE_MENU_SET",
      "id": 1,
      "quantity": 2
    }
  ]
}
```

## 실패 처리

주문 item 중 하나라도 주문 불가능하면:

```txt
주문 전체 저장 실패
orders 저장 안 함
order_items 저장 안 함
400 응답
프론트 장바구니 유지
```

부분 저장은 하지 않는다.

이유:

```txt
고객은 장바구니 전체를 주문한다고 기대한다.
일부만 저장되면 금액/수량/고객 기대가 틀어진다.
```

## 결론

현재 단계의 주문 생성은 복잡한 결제 로직이 아니다.

하지만 아래 검증은 반드시 들어가야 한다.

```txt
1. 상품 존재 여부
2. visible = true
3. status = ACTIVE
4. 주문 유형별 availableDineIn / availableTakeout
5. quantity >= 1
6. 세트 구성 존재 여부
7. 가격/이름/구성 서버 재조회
```

이 기준을 통과한 상품만 주문 스냅샷으로 저장한다.
