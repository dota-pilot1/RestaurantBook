# 한식당 키오스크 후불 시나리오

## 결론

한식당 후불 운영에서는 카드 단말기 자동 연동을 MVP의 필수 조건으로 두지 않는다.

현재 단계의 현실적인 목표는 아래 흐름이다.

```txt
고객이 키오스크/테이블 화면에서 주문
-> 주문이 DB에 저장됨
-> 주방 화면과 주방 프린터에 주문 전달
-> 직원이 음식과 고객용 주문표를 함께 전달
-> 고객은 식사 후 주문표 또는 테이블 번호로 데스크 결제
-> 직원이 관리자/데스크 화면에서 현장 결제 완료 처리
```

이 방식은 카드 단말기 연동 없이도 주문 접수, 주방 전달, 추가 주문, 결제 확인 흐름을 꽤 안정적으로 만들 수 있다.

## 포지셔닝

이 시나리오는 패스트푸드형 선결제 키오스크가 아니다.

목표는 아래에 가깝다.

```txt
한식당 후불 주문 운영 시스템
```

즉 고객이 주문 화면을 직접 사용하되, 결제는 기존 식당처럼 퇴장 시 데스크에서 처리한다.

핵심 가치는 결제 자동화가 아니라 아래에 있다.

- 직원이 2층이나 홀을 오가며 주문 받는 횟수 감소
- 주문 누락과 전달 실수 감소
- 추가 주문 편의 개선
- 주방 전달 자동화
- 고객에게 주문 내역과 결제 안내를 명확히 제공
- 데스크에서 테이블별 미결제 금액을 바로 확인

따라서 카드 단말기 자동 연동이 없어도 MVP 가치가 있다.

## 왜 후불인가

카드 단말기 연동은 키오스크 주문 화면 개발과 다른 종류의 난이도다.

필요한 것:

- 카드 단말기 또는 VAN/PG 벤더 연동
- 테스트 단말기와 테스트 가맹점 설정
- 로컬 에이전트, SDK, 플러그인, 네트워크 설정
- 승인, 실패, 취소, 타임아웃, 중복 승인 처리
- 승인됐지만 서버 저장 실패 같은 애매한 상태 복구
- 영수증, 전표, 정산, 장애 대응

따라서 MVP에서는 단말기 연동을 피하고, 기존 식당 운영처럼 데스크 카드 결제를 유지한다.

## 운영 모델

### 핵심 전제

한식당은 패스트푸드처럼 선결제가 항상 자연스럽지 않다.

일반적인 운영은 아래에 가깝다.

```txt
손님 착석
-> 주문
-> 음식 제공
-> 추가 주문
-> 식사 종료
-> 데스크 결제
```

따라서 시스템도 사람 단위보다 테이블 단위로 관리하는 것이 자연스럽다.

고객 회원가입이나 전화번호 입력은 매장 식사 주문에서는 우선순위가 낮다.

이유:

- 주문 전 전화번호 입력은 마찰이 크다.
- 단체 손님은 누가 입력할지 애매하다.
- 매장 내 주문 식별은 고객보다 테이블이 더 자연스럽다.
- 전화번호는 포장 주문, 알림, 적립, 온라인 주문에서 더 가치가 크다.

MVP에서는 `tableNo`와 `orderNo`를 식별 기준으로 둔다.

### 기본 흐름

```txt
1. 고객이 테이블 번호를 포함해 주문한다.
2. 서버가 orders / order_items / order_item_components를 저장한다.
3. 주방 화면에 새 주문이 표시된다.
4. 주방 프린터에서 주문표가 출력된다.
5. 직원이 음식과 고객용 주문표를 함께 전달한다.
6. 고객은 주문표를 보관한다.
7. 고객이 나갈 때 데스크에 주문표를 제시하거나 테이블 번호를 말한다.
8. 직원은 데스크 화면에서 미결제 주문을 조회한다.
9. 기존 카드 단말기로 결제한다.
10. 직원이 시스템에서 현장 결제 완료 처리한다.
```

## 고객용 주문표

고객용 주문표는 카드 단말기 자동 연동 전 단계에서 결제 확인을 돕는 핵심 장치다.

포함할 정보:

```txt
주문번호
테이블 번호
주문 일시
주문 유형
메뉴명
수량
금액
총액
결제 안내 문구
```

권장 안내 문구:

```txt
퇴장 전 데스크에서 결제해주세요.
결제 시 이 주문표를 제시해주세요.
```

주문표의 역할:

- 고객이 주문 내역과 총액을 확인한다.
- 직원이 음식 전달 시 주문 테이블을 간접 확인한다.
- 데스크에서 주문번호로 결제 대상을 빠르게 찾는다.
- 고객이 주문표를 테이블에 두고 가면 테이블 정리 시 미결제 여부를 확인할 수 있다.

### 주문표 전달 방식

권장 운영:

```txt
주방 프린터에서 주문표 출력
-> 직원이 음식 픽업
-> 음식과 고객용 주문표를 함께 테이블에 전달
-> 고객은 주문표를 보관
-> 퇴장 시 데스크에 주문표 제시
```

이 방식은 기존 서빙 동선에 자연스럽게 얹힌다.

직원은 어차피 음식을 테이블에 가져다주므로, 그때 주문표를 함께 전달하면 고객 확인과 결제 안내가 동시에 이루어진다.

### 주방용 주문표와 고객용 주문표

운영형으로 가면 주문표 목적을 나누는 것이 좋다.

주방용:

```txt
테이블 번호
주문번호
메뉴명
수량
옵션/구성
조리 메모
```

고객용:

```txt
테이블 번호
주문번호
메뉴명
수량
금액
총액
결제 안내 문구
```

초기에는 한 장의 주문표를 주방 확인과 고객 전달에 같이 사용해도 된다.
나중에 필요하면 주방용 1장, 고객용 1장으로 분리한다.

## 주방 프린터

처음부터 테이블마다 프린터를 둘 필요는 없다.

권장:

```txt
주방 프린터 1대
데스크는 화면 조회
필요해지면 데스크 프린터 추가
```

주방 프린터 1대 방식의 장점:

- 주문 누락 감소
- 주방이 화면을 계속 보지 않아도 됨
- 직원이 음식과 주문표를 함께 전달 가능
- 테이블별 프린터보다 설치, 용지, 장애 관리가 훨씬 단순함

프린터 출력 단계:

```txt
MVP: 주방 화면에서 수동 인쇄 또는 브라우저 기본 인쇄
운영형: 로컬 프린터 에이전트 또는 ESC/POS 프린터 자동 출력
```

### 데스크 프린터는 후순위

처음부터 프린터 2대는 과할 가능성이 높다.

권장 순서:

```txt
1. 주방 프린터 1대
2. 데스크는 화면 조회
3. 필요하면 데스크 재출력/결제 영수증 프린터 추가
```

데스크 프린터가 필요한 상황:

- 고객 주문표 분실 시 재출력
- 포장/픽업 번호표
- 결제 후 영수증 출력
- 정산용 출력

하지만 MVP에서는 데스크 화면 조회만으로도 충분하다.

## 데스크 화면

후불 모델에서 가장 중요한 화면은 데스크의 미결제 주문 조회 화면이다.

필수 기능:

- 테이블별 미결제 주문 목록
- 주문번호 검색
- 테이블 번호 검색
- 주문 총액 표시
- 추가 주문 포함 합산 표시
- 현장 결제 완료 버튼
- 결제 완료 주문과 미결제 주문 구분
- 오래된 미결제 테이블 강조
- 계산 요청 상태 표시
- 주문표 재출력 버튼

예시:

```txt
테이블 12
- 주문 20260507182538-3297
- 주문 20260507183346-2225
- 총 3개
- 총액 30,400원
- 상태: 미결제
- [현장 결제 완료]
```

### 데스크 화면의 책임

데스크 화면은 결제 단말기 자동 연동을 대체하는 운영 중심 화면이다.

책임:

```txt
어느 테이블이 얼마를 아직 결제하지 않았는지 보여준다.
고객이 주문표를 들고 오면 주문번호로 빠르게 찾는다.
고객이 테이블 번호만 말해도 미결제 주문을 찾는다.
직원이 기존 카드 단말기로 결제한 뒤 시스템에서 PAID 처리한다.
```

데스크 화면이 잘 만들어지면 프린터나 카드 단말기 자동 연동 없이도 후불 운영이 가능하다.

## 추가 주문

추가 주문은 기존 주문 row를 수정하지 않고 새 주문 row로 저장한다.

```txt
첫 주문 접수
-> orders #1 저장

추가 주문 접수
-> orders #2 저장
```

프론트에서는 같은 키오스크 세션의 주문들을 `acceptedOrders`로 묶어서 보여줄 수 있다.

서버 DB에 영속적인 묶음 컬럼은 현재 MVP에서는 필수로 두지 않는다.

이유:

- 현재 결제 도메인이 없다.
- 새로고침 복구까지는 MVP 범위가 아니다.
- 결제 구현 시 `orderIds` 배열로 결제 요청을 만들 수 있다.
- 필요해지면 `checkout_session`, `bill`, `table_session` 같은 묶음 개념을 후속 설계한다.

### 화면에서의 추가 주문

화면에서는 기존 접수 주문과 새 장바구니를 구분한다.

```txt
접수된 주문
- 이미 DB에 저장된 주문
- 주문번호가 있음
- 데스크 결제 대상

추가 장바구니
- 아직 DB에 저장되지 않은 새 주문 후보
- 추가 주문 접수하기를 눌러야 저장됨
```

추가 주문 접수 후에는 `orders` row가 하나 더 생긴다.

이후 데스크 화면에서는 같은 테이블의 미결제 주문들을 합산해서 보여준다.

## 결제 처리

MVP에서는 카드 단말기 자동 연동을 하지 않는다.

대신:

```txt
고객이 데스크에서 기존 카드 단말기로 결제
-> 직원이 데스크 화면에서 현장 결제 완료 클릭
-> 시스템의 paymentStatus를 PAID로 변경
```

후속 결제 수단:

- 카카오페이/토스페이 QR 결제
- 웹 결제 링크
- 토스플레이스 같은 단말기 플랫폼 검토
- 카드 단말기 직접 연동

우선순위는 아래가 현실적이다.

```txt
1. 후불 현장 결제 완료
2. QR/웹 결제
3. 단말기 연동 스파이크
4. 운영형 단말기 결제
```

### 현장 결제 완료 처리

현장 결제 완료는 직원이 직접 누르는 수동 처리다.

버튼을 누르기 전 직원이 확인해야 할 것:

```txt
고객이 제시한 주문표 또는 테이블 번호
데스크 화면의 미결제 주문 목록
기존 카드 단말기 승인 완료 여부
현금/계좌이체 등 다른 결제 완료 여부
```

버튼 클릭 후 시스템 처리:

```txt
대상 주문들의 paymentStatus = PAID
paidAt 저장
paymentMethod = ON_SITE_CARD 또는 CASH 등으로 저장
처리 직원 id 저장
```

결제 도메인이 생기기 전에는 최소한 주문의 결제 상태만 분리해도 된다.

## 상태 설계 후보

주문 상태와 결제 상태는 분리하는 것이 좋다.

주문 상태:

```txt
RECEIVED
COOKING
READY
SERVED
CANCELED
```

결제 상태:

```txt
UNPAID
PAID
REFUNDED
```

테이블 상태 후보:

```txt
OCCUPIED
NEED_PAYMENT
CLOSED
```

초기 구현에서는 `orders.status = RECEIVED`까지만 있어도 된다.
주방 보드와 데스크 결제 화면을 구현할 때 상태를 확장한다.

### 상태 분리 이유

주문 진행 상태와 결제 상태는 서로 다른 축이다.

예:

```txt
주문은 SERVED지만 아직 UNPAID일 수 있다.
주문은 RECEIVED지만 QR 선결제로 PAID일 수 있다.
주문은 CANCELED이면 결제도 취소/환불 상태를 봐야 한다.
```

따라서 장기적으로는 아래를 분리한다.

```txt
orders.status
orders.payment_status
```

결제 테이블이 생기면 `payments.status`도 별도로 둔다.

## 화면 구성 후보

### 고객 주문 화면

필수:

- 테이블 번호 표시
- 메뉴 조회
- 장바구니
- 주문 접수
- 추가 주문
- 접수된 주문 내역
- 결제 안내

후불 안내 문구:

```txt
결제는 식사 후 데스크에서 진행해주세요.
음식과 함께 전달되는 주문표를 보관해주세요.
```

### 주방 화면

필수:

- 새 주문 알림
- 테이블 번호
- 주문번호
- 메뉴/수량/세트 구성
- 조리 상태 변경
- 주문표 출력/재출력

### 데스크 화면

필수:

- 테이블별 미결제 주문
- 주문번호 검색
- 테이블 번호 검색
- 합산 금액
- 현장 결제 완료
- 결제 완료 내역 조회

### 홀/서빙 화면

MVP에서는 별도 태블릿을 들고 다니는 방식은 우선순위가 낮다.

대신:

```txt
주방 옆 고정 태블릿
데스크 화면
주방 프린터 주문표
```

이 세 가지로 먼저 운영한다.

## 구현 우선순위

### 1단계: 현재 주문 MVP

이미 진행 중인 범위:

- 고객 주문 생성 API
- 주문 item 저장
- 세트 구성 스냅샷 저장
- 프론트 장바구니 주문 접수
- 추가 주문 UX

### 2단계: 테이블 번호

필수 추가:

- 주문 요청에 `tableNo` 추가
- `orders.table_no` 저장
- 고객 화면에서 테이블 번호 설정 또는 URL 파라미터 사용

예:

```txt
/customer?tableNo=12
```

테이블 QR을 사용할 경우:

```txt
테이블마다 /customer?tableNo=12 형태의 QR 배치
고객은 QR 스캔 후 해당 테이블로 주문
```

키오스크 한 대를 공용으로 사용할 경우:

```txt
주문 전 테이블 번호 선택
또는 직원이 테이블 번호를 입력
```

### 3단계: 주방 보드

필수 기능:

- 새 주문 목록
- 테이블 번호 표시
- 주문번호 표시
- 메뉴/수량 표시
- 주문 상태 변경

### 4단계: 주방 프린터

MVP:

- 주문 상세 인쇄 화면
- 브라우저 인쇄
- 주방 PC 기본 프린터 사용

운영형:

- 자동 출력
- ESC/POS 지원
- 출력 실패 재시도
- 재출력 버튼

### 5단계: 데스크 미결제 화면

필수 기능:

- 테이블별 미결제 주문 조회
- 추가 주문 합산
- 주문번호 검색
- 현장 결제 완료 처리
- 결제 완료 처리 직원 기록
- 주문표 재출력

### 6단계: QR/웹 결제

후속:

- `orderIds` 기반 결제 요청
- 카카오페이/토스페이 QR 또는 결제 링크
- 결제 성공 callback/webhook
- 결제 상태 변경

### 7단계: 결제 단말기 연동 검토

후속 검토:

- 토스플레이스 프론트 연동 가능 여부
- 일반 Next.js 웹 키오스크에서 단말기 결제 요청 가능 여부
- 로컬 에이전트 필요 여부
- 테스트 단말기 제공 여부
- 승인/취소/타임아웃 처리 방식
- 실제 매장 설치/검수 방식

단말기 연동은 별도 스파이크 작업으로 분리한다.

## 데이터 설계 후보

### orders 추가 후보

후불 운영을 위해 이후 추가될 수 있는 필드:

```txt
table_no
payment_status
served_at
paid_at
paid_by_user_id
payment_method
```

초기에는 `table_no`, `payment_status`가 가장 중요하다.

### payment_status 후보

```txt
UNPAID
PAID
CANCELED
REFUNDED
```

### payment_method 후보

```txt
ON_SITE_CARD
CASH
BANK_TRANSFER
KAKAO_PAY
TOSS_PAY
UNKNOWN
```

단말기 자동 연동 전에는 `ON_SITE_CARD`를 직원 수동 처리용으로 둔다.

### 주문 묶음 후보

MVP에서는 필수 아님.

후속 후보:

```txt
table_session_id
checkout_session_id
bill_id
```

필요해지는 시점:

- 새로고침 후에도 같은 손님 주문 묶음을 복구해야 할 때
- 테이블 착석/퇴장 단위를 명확히 관리해야 할 때
- 여러 주문을 하나의 결제 세션으로 영속 관리해야 할 때
- QR/웹 결제 실패/재시도 상태를 서버에서 관리해야 할 때

현재는 테이블 번호와 미결제 상태로 먼저 운영한다.

## 리스크와 대응

### 무전취식

시스템만으로 완전히 막을 수 없다.
기존 후불 식당과 마찬가지로 운영 동선, 직원 확인, CCTV가 필요하다.

시스템이 할 수 있는 것:

- 미결제 테이블 강조
- 오래된 미결제 주문 표시
- 테이블 정리 전 결제 여부 확인
- 주문표를 통한 결제 안내

운영 대응:

- 출입구/데스크 동선 관리
- CCTV
- 직원이 퇴장 손님 확인
- 테이블 정리 시 주문표와 미결제 상태 확인

### 테이블 번호 오입력

대응:

- 테이블 QR 방식이면 오입력 가능성을 줄일 수 있다.
- 공용 키오스크 방식이면 테이블 번호 확인 화면을 둔다.
- 주문표에 테이블 번호를 크게 출력한다.
- 데스크/주방에서 테이블 번호 수정 기능을 후속으로 둔다.

### 주문표 분실

대응:

- 데스크에서 테이블 번호로 조회
- 주문번호 검색
- 재출력 기능

### 추가 주문 결제 누락

대응:

- 테이블별 미결제 주문을 합산 표시
- 결제 완료 전까지 모든 미결제 주문을 화면에 유지

### 프린터 장애

대응:

- 주방 보드를 기본 진실 소스로 유지
- 프린터는 보조 출력 수단으로 취급
- 재출력 버튼 제공

### 고객이 주문표를 안 가져오는 경우

대응:

- 테이블 번호로 조회 가능해야 한다.
- 데스크 화면에서 미결제 테이블 목록을 바로 볼 수 있어야 한다.
- 주문표는 보조 확인 수단이지 유일한 결제 수단이 아니어야 한다.

## MVP 완료 기준

후불 시나리오 1차 완료 기준:

```txt
1. 고객이 테이블 번호와 함께 주문할 수 있다.
2. 주문이 서버에 정확히 저장된다.
3. 주방 화면에서 새 주문을 볼 수 있다.
4. 주문표를 출력하거나 인쇄 화면으로 볼 수 있다.
5. 데스크 화면에서 테이블별 미결제 주문을 조회할 수 있다.
6. 직원이 현장 결제 완료 처리할 수 있다.
7. 추가 주문도 같은 테이블의 미결제 주문으로 합산 조회된다.
```

## 결론

한식당 후불 모델에서는 카드 단말기 자동 연동 없이도 충분히 의미 있는 MVP를 만들 수 있다.

핵심은 결제가 아니라 아래 흐름이다.

```txt
주문 정확히 저장
주방에 즉시 전달
고객에게 주문표 전달
데스크에서 미결제 주문 조회
기존 카드 단말기로 결제
직원이 현장 결제 완료 처리
```

이 방식은 결제 단말기 연동이라는 가장 큰 복잡도를 뒤로 미루면서도, 실제 식당 운영의 주문 동선과 주방 전달 문제를 먼저 해결한다.
