# 헤더 다중 메뉴 구현 방법

## 결론

RestaurantBook의 `관리` 메뉴는 2차/3차 구조가 필요하다.

현재처럼 `관리` 드롭다운 안에 모든 관리 페이지를 평면으로 넣으면, 고객 키오스크 메뉴 관리가 추가되는 순간 `메뉴 관리`라는 이름이 충돌한다.

따라서 상단 헤더는 다음 구조가 적합하다.

```txt
1차: 관리
2차: 운영 관리 / 상품 관리 / 사람·권한 / 설정
3차: 실제 이동 페이지
```

BeautyBook의 관리 메가메뉴 방식처럼, `관리` 버튼을 누르면 넓은 패널이 열리고 패널 내부에서 기능을 그룹별 카드로 보여주는 방식이 좋다.

## 메뉴 명칭 정리

`메뉴 관리`라는 이름은 두 의미가 섞이기 쉽다.

현재 RestaurantBook에는 최소 두 종류의 메뉴가 있다.

```txt
1. 헤더 메뉴
   - 상단 네비게이션에 노출되는 앱 메뉴
   - 예: 대시보드, 관리, 유저 관리, 롤 관리

2. 판매 메뉴
   - 고객 키오스크에서 주문하는 음식/상품 메뉴
   - 예: 대표 한상 세트, 제육 덮밥, 식혜
```

따라서 명칭은 아래처럼 분리한다.

```txt
/menu-management
= 헤더 메뉴 관리 또는 네비게이션 관리

새로 만들 키오스크 메뉴 CRUD
= 판매 메뉴 관리
```

추천 명칭은 다음과 같다.

```txt
헤더 메뉴 관리
판매 메뉴 관리
카테고리 관리
옵션/토핑 관리
품절/노출 관리
```

`메뉴 관리`라는 단독 명칭은 되도록 쓰지 않는다.

## 현재 RestaurantBook 상태

현재 프론트 헤더는 메뉴 데이터를 트리로 만드는 구조를 이미 갖고 있다.

파일:

```txt
restaurant-book-front/src/widgets/header/ui/Header.tsx
restaurant-book-front/src/entities/menu/model/types.ts
restaurant-book-front/src/entities/menu/api/menuApi.ts
```

`MenuRecord`는 `parentId`를 가지고 있고, 프론트의 `buildTree()`도 재귀 트리 구조를 만든다.

즉 데이터 구조상으로는 2차/3차 메뉴를 만들 수 있다.

다만 현재 헤더 렌더링은 실질적으로 2단계까지만 표현한다.

```txt
현재:
관리
├─ 유저 관리
├─ 롤 관리
├─ 역할-권한 매핑
├─ 메인 관리
└─ 메뉴 관리
```

3차 구조를 실제 UI로 쓰려면 `관리` 메뉴만 별도 메가메뉴 컴포넌트로 렌더링하는 것이 좋다.

## 헤더 구현 방식

### 1. 트리 빌드는 유지

현재 `buildTree()` 구조는 유지한다.

```ts
function buildTree(flat: MenuRecord[], userRole: string | null): MenuItem[] {
  const visible = flat.filter(
    (m) => m.visible && (!m.requiredRole || m.requiredRole === userRole)
  );

  const map = new Map<number, MenuItem>();
  visible.forEach((m) => map.set(m.id, { ...m, children: [] }));

  const roots: MenuItem[] = [];
  map.forEach((item) => {
    if (item.parentId === null) roots.push(item);
    else map.get(item.parentId)?.children.push(item);
  });

  return sort(roots);
}
```

### 2. ADMIN만 메가메뉴로 분기

```ts
function NavItem({ item }: { item: MenuItem }) {
  if (item.children.length > 0) {
    if (item.code === "ADMIN") {
      return <AdminMegaMenu item={item} />;
    }
    return <DropdownMenu item={item} />;
  }

  return (
    <NavLink href={item.path ?? "#"} exact={item.path === "/dashboard"}>
      {item.label}
    </NavLink>
  );
}
```

### 3. AdminMegaMenu는 2차 그룹과 3차 링크를 표현

```tsx
function AdminMegaMenu({ item }: { item: MenuItem }) {
  const groups = item.children;

  return (
    <div className="relative">
      <button>관리</button>

      <div className="absolute left-1/2 top-full z-50">
        <aside>
          <p>ADMIN</p>
          <h3>관리 센터</h3>
          <Link href="/dashboard">대시보드</Link>
        </aside>

        <section>
          {groups.map((group) => (
            <div key={group.id}>
              <h4>{group.label}</h4>
              {group.children.map((child) => (
                <Link key={child.id} href={child.path ?? "#"}>
                  {child.label}
                </Link>
              ))}
            </div>
          ))}
        </section>
      </div>
    </div>
  );
}
```

### 4. active 판단은 하위 leaf까지 검사

관리 버튼이 활성 상태인지 판단할 때는 3차 하위 링크까지 본다.

```ts
function flattenLeaves(item: MenuItem): MenuItem[] {
  if (item.children.length === 0) return item.path ? [item] : [];
  return item.children.flatMap(flattenLeaves);
}

const leaves = flattenLeaves(item);
const isActive = leaves.some((leaf) => leaf.path && pathname.startsWith(leaf.path));
```

## 메뉴 관리 화면 개선 포인트

현재 `MenuTreeTab`은 재귀 트리 렌더링을 하므로 3차 메뉴 표시가 가능하다.

다만 부모 메뉴 선택이 루트 중심이라 3차 추가 UX가 약하다.

개선 방향:

```txt
1. 부모 메뉴 select에 모든 메뉴를 depth 들여쓰기 형태로 노출
2. 현재 메뉴 자기 자신과 하위 메뉴는 부모 후보에서 제외
3. depth가 3을 넘는 부모 선택은 막기
4. 그룹 노드는 path를 비워도 저장 가능
5. 실제 링크 노드는 path 입력을 권장
```

부모 메뉴 select 예시:

```txt
없음 (루트)
관리
  운영 관리
  상품 관리
    판매 메뉴 관리
    카테고리 관리
  사람·권한
  설정
```

## 구현 순서

추천 순서:

```txt
1. 용어 정리
   - 기존 메뉴 관리 → 헤더 메뉴 관리
   - 신규 키오스크 음식 메뉴 → 판매 메뉴 관리

2. MenuSeeder 구조 변경
   - ADMIN 아래에 2차 그룹 노드 추가
   - 기존 관리 링크를 적절한 그룹 아래로 이동

3. Header에 AdminMegaMenu 추가
   - ADMIN만 메가메뉴로 렌더링
   - 일반 드롭다운은 기존 유지

4. MenuTreeTab 개선
   - 부모 선택에서 2차/3차 추가가 쉽게 보이도록 변경
   - depth 제한 추가

5. 키오스크 판매 메뉴 도메인 추가
   - 판매 메뉴 관리 페이지 생성
   - 고객 `/customer` 키오스크 화면이 이 데이터를 읽도록 연결
```

## 최종 판단

RestaurantBook은 BeautyBook 방식처럼 가는 것이 좋다.

이유:

```txt
1. 관리자 기능이 늘어날수록 평면 드롭다운은 금방 복잡해진다.
2. 판매 메뉴 관리와 헤더 메뉴 관리를 명확히 분리할 수 있다.
3. 2차 그룹으로 운영자의 인지 부담이 줄어든다.
4. 3차 실제 링크를 카드 형태로 보여주면 클릭 목표가 명확하다.
5. 기존 MenuRecord parentId 구조를 그대로 활용할 수 있다.
```

따라서 방향은 다음으로 확정한다.

```txt
상단 헤더:
관리 = 메가메뉴

2차:
운영 관리 / 상품 관리 / 사람·권한 / 설정

3차:
실제 관리 페이지 링크

기존 /menu-management:
헤더 메뉴 관리

신규 키오스크 메뉴 CRUD:
판매 메뉴 관리
```
