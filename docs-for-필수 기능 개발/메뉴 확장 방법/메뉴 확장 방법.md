# 메뉴 확장 방법

## 결론

메뉴 확장은 initializer/seeder로 기본 메뉴를 보장하는 방식이 바람직하다.

다만 initializer가 운영자가 메뉴 관리에서 바꾼 값을 계속 덮어쓰면 안 된다.

역할 분담은 아래처럼 잡는다.

```txt
initializer / seeder
= 앱이 동작하기 위한 기본 메뉴 코드와 최초 구조를 보장

메뉴 관리 화면
= 노출 여부, 순서, 라벨, 부모 메뉴, 아이콘, 권한을 운영자가 조정
```

즉 “페이지를 만들고 메뉴를 추가하면 보일지 말지는 메뉴 관리에서 설정한다”는 방향이 맞다.

## 왜 initializer가 필요한가

메뉴를 전부 관리자 UI에서만 만들게 하면 다음 문제가 생긴다.

```txt
1. 새 환경에서 기본 메뉴가 없어 앱 진입이 막힐 수 있다.
2. 새 기능 페이지를 배포했는데 운영자가 직접 메뉴를 만들기 전까지 접근 경로가 없다.
3. 개발/스테이징/운영 환경의 메뉴 코드가 서로 달라질 수 있다.
4. 권한/역할 기반 메뉴 필터링 기준이 흔들릴 수 있다.
```

따라서 새 기능을 추가할 때는 코드에 메뉴 정의를 함께 두는 것이 좋다.

하지만 initializer는 “초기 생성”에 가깝게 동작해야 한다.

## 현재 구조

현재 서버 메뉴 initializer:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/config/MenuSeeder.java
```

현재 메뉴 도메인:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/menu/domain/Menu.java
```

현재 메뉴 테이블은 다음 필드를 가진다.

```txt
code
parent
label
labelKey
path
icon
isExternal
requiredRole
requiredPermission
visible
displayOrder
```

프론트는 `/api/menus`에서 메뉴 목록을 가져와 `parentId` 기준 트리로 만든다.

```txt
restaurant-book-front/src/widgets/header/ui/Header.tsx
restaurant-book-front/src/entities/menu/api/menuApi.ts
restaurant-book-front/src/entities/menu/model/types.ts
```

## 현재 MenuSeeder의 주의점

현재 `MenuSeeder`는 기존 메뉴가 있으면 `existing.update(...)`를 호출한다.

```java
menuRepository.findByCode(def.code()).ifPresentOrElse(
    existing -> existing.update(...),
    () -> menuRepository.save(...)
);
```

이 방식은 개발 중에는 편하지만, 운영 설정과 충돌할 수 있다.

예를 들어 관리자가 메뉴 관리에서 아래 값을 바꿨다고 하자.

```txt
라벨: 메뉴 관리 → 헤더 메뉴 관리
visible: true → false
displayOrder: 4 → 8
parent: 관리 → 설정
```

서버가 다시 뜰 때 seeder가 `update()`를 수행하면 운영자가 바꾼 값이 다시 코드 기본값으로 돌아갈 수 있다.

따라서 운영형 메뉴 initializer는 아래 원칙을 따라야 한다.

```txt
없는 메뉴는 생성한다.
있는 메뉴는 운영자가 바꿀 수 있는 필드를 함부로 덮어쓰지 않는다.
```

## 권장 방식

### 1. 메뉴 code는 불변 키로 본다

`code`는 메뉴의 시스템 식별자다.

```txt
ADMIN
ADMIN_OPERATIONS
ADMIN_PRODUCTS
ADMIN_PEOPLE
ADMIN_SETTINGS
ADMIN_NAV_MANAGEMENT
ADMIN_SALE_MENU
```

운영자가 라벨이나 순서를 바꾸더라도 `code`는 유지해야 한다.

### 2. 신규 메뉴는 initializer로 생성한다

새 페이지를 만들 때는 initializer에 메뉴 정의를 추가한다.

예:

```txt
페이지 생성:
restaurant-book-front/src/app/sale-menus/page.tsx

initializer 추가:
ADMIN_SALE_MENU
label: 판매 메뉴 관리
path: /sale-menus
parent: ADMIN_PRODUCTS
requiredRole: ROLE_ADMIN
visible: true
```

### 3. 기존 메뉴는 가능하면 덮어쓰지 않는다

운영자가 메뉴 관리에서 바꿀 수 있는 값은 initializer가 보존해야 한다.

보존 권장 필드:

```txt
label
labelKey
parent
icon
visible
displayOrder
requiredRole
requiredPermission
```

반대로 코드에서 강하게 보장해야 할 수 있는 필드:

```txt
code
```

`path`는 판단이 필요하다.

페이지 경로가 바뀐 경우 initializer로 업데이트해야 할 수도 있지만, 운영자가 커스텀 링크를 바꿀 수도 있다.

초기 단계에서는 `path`도 운영자가 바꿀 수 있는 값으로 보고 덮어쓰지 않는 편이 안전하다.

경로 변경이 꼭 필요하면 별도 마이그레이션으로 처리한다.

## 추천 initializer 정책

### 개발 초기

초기 개발 중에는 `upsert` 방식도 괜찮다.

```txt
앱을 다시 띄울 때마다 메뉴 구조가 코드 기준으로 정리됨
```

장점:

```txt
개발 속도가 빠르다.
메뉴 구조 변경이 즉시 반영된다.
```

단점:

```txt
메뉴 관리 화면에서 바꾼 값이 재시작 때 덮어써질 수 있다.
```

### 운영 전환 전

운영에 가까워지면 `create-if-missing` 방식으로 바꾼다.

```txt
없는 메뉴만 생성
있는 메뉴는 건드리지 않음
```

추천 방식:

```java
menuRepository.findByCode(def.code()).ifPresentOrElse(
    existing -> {
        // 기본 메뉴가 이미 있으면 운영 설정을 존중한다.
    },
    () -> menuRepository.save(...)
);
```

단, 시스템 필수 메뉴의 parent 관계가 깨졌거나 code 중복이 생기는 문제는 별도 검증 로그로 감지한다.

## 메뉴 확장 작업 순서

새 기능 페이지를 추가할 때의 표준 순서:

```txt
1. 프론트 페이지 생성
   예: /sale-menus

2. 권한 가드 설정
   예: ROLE_ADMIN 전용

3. 서버 initializer에 메뉴 code 추가
   예: ADMIN_SALE_MENU

4. 로컬에서 서버 재시작
   메뉴가 없으면 자동 생성

5. 메뉴 관리 화면에서 노출 여부/순서/라벨 확인

6. 헤더에서 표시 확인
```

이때 “보이냐 마냐”는 메뉴 관리의 `visible` 값으로 결정한다.

```txt
visible = true
→ 헤더 노출

visible = false
→ 헤더 숨김
```

하지만 페이지 접근 권한은 `visible`만으로 막으면 안 된다.

페이지 자체에는 별도 guard가 필요하다.

```txt
메뉴 노출 제어
= UX 제어

페이지 권한 guard
= 보안 제어
```

## 2차/3차 메뉴 확장 기준

RestaurantBook 관리 메뉴는 아래 구조를 기준으로 확장한다.

```txt
관리
├─ 운영 관리
│  ├─ 대시보드
│  ├─ 주문 관리
│  ├─ 주방 현황
│  └─ 매출 관리
├─ 상품 관리
│  ├─ 판매 메뉴 관리
│  ├─ 카테고리 관리
│  ├─ 옵션/토핑 관리
│  └─ 품절/노출 관리
├─ 사람·권한
│  ├─ 유저 관리
│  ├─ 롤 관리
│  └─ 역할-권한 매핑
└─ 설정
   ├─ 매장 설정
   ├─ 화면 설정
   └─ 헤더 메뉴 관리
```

여기서 2차 그룹 노드는 보통 `path = null`이다.

```txt
ADMIN_PRODUCTS
label: 상품 관리
path: null
```

3차 실제 페이지 노드는 `path`를 가진다.

```txt
ADMIN_SALE_MENU
label: 판매 메뉴 관리
path: /sale-menus
```

## 명칭 원칙

`메뉴 관리`라는 단독 명칭은 피한다.

이유:

```txt
헤더 메뉴인지
키오스크 판매 메뉴인지
의미가 충돌한다.
```

추천 명칭:

```txt
헤더 메뉴 관리
판매 메뉴 관리
카테고리 관리
옵션/토핑 관리
품절/노출 관리
```

기존 `/menu-management`는 아래처럼 이름을 바꾼다.

```txt
기존:
메뉴 관리

변경:
헤더 메뉴 관리
```

새로 만들 고객 키오스크 메뉴 관리 화면은 아래처럼 둔다.

```txt
판매 메뉴 관리
```

## 메뉴 관리 화면의 역할

메뉴 관리 화면은 운영자가 메뉴 노출을 조정하는 곳이다.

가능해야 하는 일:

```txt
1. 라벨 변경
2. 부모 메뉴 변경
3. 노출 여부 변경
4. 표시 순서 변경
5. 아이콘 변경
6. 필요 역할/권한 변경
7. 외부 링크 여부 변경
```

initializer는 이 값들을 “기본값”으로만 제공해야 한다.

## 데이터 보존 기준

추천 정책:

```txt
신규 code
→ initializer가 생성

기존 code
→ 운영자가 바꾼 값을 유지

삭제된 code
→ 자동 재생성 여부는 정책 필요
```

삭제 정책은 둘 중 하나를 선택한다.

### 선택 A: 삭제된 기본 메뉴는 재생성

장점:

```txt
필수 메뉴가 사라지는 사고를 막는다.
```

단점:

```txt
운영자가 의도적으로 삭제한 메뉴가 다시 생길 수 있다.
```

### 선택 B: 삭제 대신 숨김만 허용

추천은 선택 B다.

기본 시스템 메뉴는 삭제하지 않고 `visible = false`로 숨기는 방식이 더 안전하다.

향후 `systemMenu` 같은 필드를 추가하면 더 명확해진다.

```txt
systemMenu = true
→ 삭제 불가
→ 숨김 가능
→ 라벨/순서 변경 가능
```

현재 테이블에는 `systemMenu`가 없으므로 우선 운영 규칙으로 둔다.

## 향후 개선안

운영 안정성을 높이려면 메뉴 테이블에 아래 필드를 추가하는 것도 좋다.

```txt
systemMenu boolean
locked boolean
lastSeedVersion string
```

의미:

```txt
systemMenu
= 코드에서 제공하는 기본 메뉴

locked
= 운영자가 삭제/부모변경하지 못하게 할지 여부

lastSeedVersion
= 어느 메뉴 시드 버전에서 생성됐는지 추적
```

하지만 지금 단계에서는 과하다.

현재는 아래 정책이면 충분하다.

```txt
code는 initializer로 보장
노출/순서/라벨은 메뉴 관리에서 조정
기존 메뉴는 seeder가 덮어쓰지 않도록 개선
```

## 최종 권장안

RestaurantBook 메뉴 확장은 다음 정책으로 간다.

```txt
1. 새 페이지를 만들 때 initializer에 기본 메뉴를 추가한다.
2. initializer는 없는 메뉴만 만든다.
3. 운영자가 메뉴 관리에서 바꾼 값은 보존한다.
4. 메뉴 노출 여부는 메뉴 관리의 visible로 결정한다.
5. 페이지 접근 권한은 별도 RequireRole/RequireAuth로 막는다.
6. 기존 /menu-management는 헤더 메뉴 관리로 명칭을 바꾼다.
7. 고객 키오스크 음식 메뉴는 판매 메뉴 관리로 별도 도메인을 만든다.
```

즉 initializer는 필요하다.

하지만 initializer는 운영 메뉴 설정의 주인이 아니라, 기본 메뉴 구조를 보장하는 보조 장치여야 한다.
