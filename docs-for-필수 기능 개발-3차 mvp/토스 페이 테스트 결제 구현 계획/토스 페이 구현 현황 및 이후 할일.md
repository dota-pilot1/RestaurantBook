# 토스 페이 구현 현황 및 이후 할일

작성일: 2026-05-10

## 결론

고객 키오스크의 `READY(조리 완료/결제 대기)` 주문을 토스 테스트 결제로 결제하는 흐름은 구현 및 운영 배포까지 완료했다.

현재 구조는 후불 결제를 기본으로 한다. 고객은 결제 대기 주문 중 1건만 결제하거나 여러 건을 묶어 한 번의 토스 결제창으로 결제할 수 있다. 주문 금액을 쪼개는 분할 결제는 지원하지 않는다.

## 결제수단 분류 현황

현재 설계는 회계/매출 집계용 결제수단과 PG 원본 결제수단을 분리한다.

- `PaymentMethod`
  - 매출 집계용 큰 분류
  - 현재 값: `CARD`, `CASH`, `EASY_PAY`, `TRANSFER`, `ETC`
- `provider`
  - PG 제공자
  - 토스 결제는 `TOSS`
- `providerMethod`
  - 고객/직원 화면에 보여줄 실제 결제수단 라벨
  - 예: `카카오페이`, `토스페이`, `네이버페이`, `카드`, `계좌이체`

정책:

- 직원 수동 결제는 계속 `카드`, `현금`, `기타` 중심으로 둔다.
- 고객 토스 결제창에서 카카오페이 같은 간편결제가 선택되면 `PaymentMethod.EASY_PAY`로 집계하고 `providerMethod`에 실제 브랜드를 저장한다.
- 식당 운영상 가상계좌/휴대폰 결제는 우선순위가 낮다.
- 계좌이체는 필요하면 `TRANSFER`로 집계할 수 있게 열어뒀다.

## 프론트 구현 현황

### 고객 키오스크

완료:

- 기존 결제 다이얼로그 흐름을 유지하면서 토스 결제를 연결했다.
- 기본 결제 정책은 후불이다.
- 결제 버튼은 `READY` 주문이 있을 때 활성화된다.

  - 단건 결제: 주문 1건만 선택
  - 다건 결제: 여러 `READY` 주문을 묶어서 결제
- 토스 결제창은 선택된 주문 묶음에 대해 1번만 연다.
- 성공 페이지에서 백엔드 confirm API를 호출한다.

## 이후 할일

### 우선순위 높음

- 운영 환경에서 실제 토스 테스트 결제 시나리오를 한 번 더 끝까지 수행한다.
- 중복 confirm 재호출 케이스를 운영 또는 로컬에서 명시적으로 재검증한다.
- `about2/page.tsx`의 unused `ChevronRight` 린트 경고를 제거한다.
- `PaymentSchemaMigrator`가 운영 DB에서 반복 실행돼도 불필요한 로그나 부작용이 없는지 한 번 더 확인한다.
- 운영 DB 백업 정책을 확인한 뒤 결제 테이블 마이그레이션 결과를 점검한다.

### 다음 결제 고도화

- 토스 결제 취소 API를 기존 환불 API와 연결한다.
- 현재 환불은 우선 `Payment` 단위 전체 환불 정책으로 유지한다.
- 토스 결제 취소 성공 응답과 내부 `PaymentRefund` 저장을 하나의 트랜잭션 정책으로 정리한다.
- 웹훅 또는 결제 상태 재조회 보정 정책을 설계한다.
- 토스 실결제 전환 시 테스트 키/라이브 키, 허용 도메인, 리다이렉트 URL, 결제 UI 설정을 다시 점검한다.
- `TOSS_PAYMENTS_SECURITY_KEY`는 웹훅 검증을 붙일 때 사용 여부를 결정한다.

### UX 후속

- 결제 방식 선택 다이얼로그의 단건/다건 표현을 실제 고객 테스트 후 더 다듬는다.
- `다건 결제`가 가능한 경우 기본 선택을 전체 결제로 둘지, 방식 선택을 계속 먼저 보여줄지 운영 피드백을 받는다.
- 후불 결제 안내 문구는 현재 고객 기준으로 충분하지만, 매장 정책이 선불/후불 혼합으로 바뀌면 문구를 다시 조정한다.
- 토스 결제창에서 노출되는 결제수단 중 식당 운영에 맞지 않는 수단을 제한할 수 있는지 토스 관리자 설정을 확인한다.

  - 이미 구현된 항목인 `여러 READY 주문 선택 결제 UI`, `providerMethod 저장`, `payment_orders` 구조 등을 완료 처리한다.
  - 아직 남은 항목인 토스 환불 API, 웹훅, 운영 실결제 전환은 미완료로 유지한다.
