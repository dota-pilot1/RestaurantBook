# 추후 실결제 구현에 대한 참고사항

## 요약

현재 `Payment` 도메인은 결제 1건을 저장하는 기본 형태로는 적절하다.  
하지만 실제 매장 결제는 대표 결제, 각자 결제, 선결제, 후불 결제가 모두 나올 수 있으므로 `Payment`와 `Order`를 직접 1:1로 고정하지 않고 `payment_orders` 연결 테이블을 둔다.

핵심 정책:

- 전체 결제와 선택 주문 결제를 모두 허용할 수 있는 구조로 간다.
- 주문별로 결제 버튼을 여러 번 강제하지 않는다.
- 고객이 원하면 결제 대기 주문 중 일부만 선택해서 결제할 수 있다.
- 주문 1건의 금액을 쪼개는 분할 결제는 제외한다.
- 결제 1건은 주문 1건 또는 여러 건을 포함할 수 있다.
- 결제 후 기준으로 주문 1건은 `payment_orders` 1건에만 연결된다.

## 현재 구조의 장점

- `PaymentStatus`가 있어 `PAID`, `REFUNDED` 기준 매출/환불 집계가 가능하다.
- `Order COMPLETED`와 `Payment PAID`를 같은 트랜잭션에서 처리하기 쉽다.
- 현재 직원 보드, 매출 요약, 환불 흐름과 잘 맞는다.
- `Payment`를 결제 헤더로 유지하면 단건 결제, 선택 주문 결제, 전체 합산 결제를 같은 구조로 처리할 수 있다.

## 현재 구조의 한계

- 토스 `paymentKey`를 저장하지 않으면 토스 결제 조회/취소/환불을 안정적으로 할 수 없다.
- 토스 `orderId`를 저장하지 않으면 내부 주문번호와 PG 주문번호를 대조하기 어렵다.
- 토스 원본 `method`를 저장하지 않으면 카드/간편결제/계좌이체 구분이 흐려진다.
- 영수증 URL을 저장하지 않으면 고객/직원 화면에서 결제 증빙을 바로 열기 어렵다.
- 여러 주문을 하나의 결제로 묶으려면 현재 `payments.order_id unique` 구조를 제거하고 `payment_orders` 연결 테이블을 추가해야 한다.

## 권장 확장안

### 1. 핵심 테이블 구조

핵심 테이블:

```text
payments
payment_orders
payment_refunds
```

역할:

```text
payments
= 실제 결제 1건
= 토스 승인 1번, 카드 결제 1번, 현금 결제 1번
= 총 결제금액, 결제수단, 결제상태, PG 식별자 저장
```

```text
payment_orders
= 결제 1건에 포함된 주문 연결 정보
= 각 행은 orders 테이블의 주문 1건을 참조
= 결제 후 기준으로 Order 1건과 PaymentOrder 1건은 1:1
```

```text
payment_refunds
= 환불 이력
= 초기에는 Payment 단위 전체 환불을 우선 고려
```

관계:

```text
Payment 1 : N PaymentOrder
Order   1 : 0..1 PaymentOrder
```

결제 후 기준:

```text
Order 1 : 1 PaymentOrder
```

권장 제약:

```text
payment_orders.payment_id FK -> payments.id
payment_orders.order_id FK -> orders.id
unique(payment_orders.order_id)
```

`unique(payment_orders.order_id)`는 한 주문이 여러 결제에 중복 포함되는 것을 막는다. 주문 금액을 쪼개는 분할 결제를 제외하므로 이 제약이 적절하다.

이 구조에서 가능한 결제 정책:

```text
전체 결제
- READY 주문 전체 선택
- Payment 1건
- PaymentOrder N건
```

```text
선택 결제 / 각자 결제
- 고객이 특정 주문만 선택
- Payment 1건
- PaymentOrder 일부 주문 N건
```

```text
단건 결제
- 주문 1건 선택
- Payment 1건
- PaymentOrder 1건
```

```text
선결제
- 주문 생성 직후 Payment 생성
- PaymentOrder 연결
- 이후 주문은 조리 흐름 진행
```

### 2. `payments` 컬럼 확장

운영 전환 전 우선순위가 높은 컬럼:

```text
provider varchar(20)              -- TOSS, MANUAL
provider_payment_key varchar(200) -- 토스 paymentKey
provider_order_id varchar(100)    -- 토스 orderId
provider_method varchar(50)       -- 토스 원본 method
receipt_url varchar(500)          -- 영수증 URL
approved_at timestamp             -- 토스 승인 시각
```

권장 제약:

```text
unique(provider, provider_payment_key)
unique(provider, provider_order_id)
```

주의:

- `provider_payment_key`는 로그에 원문을 과하게 남기지 않는다.
- 테스트 결제 단계에서는 컬럼 없이 진행할 수 있지만, 환불 API를 토스와 연결하려면 필수다.

### 3. 결제 제공자 구분

현재 `PaymentMethod`는 `CARD`, `CASH`, `ETC`라 매장 결제수단 관점에 가깝다.  
PG 연동 후에는 아래 구분을 분리하는 것이 좋다.

```text
PaymentMethod       -- 매출 집계용: CARD, CASH, ETC
PaymentProvider     -- 결제 제공자: MANUAL, TOSS
providerMethod      -- PG 원본 결제수단: 카드, 간편결제, 계좌이체 등
```

테스트 결제 단계에서는 토스 온라인 결제를 `PaymentMethod.CARD`로 저장해도 충분하다.  
실결제에서는 `providerMethod`를 별도로 저장해야 정산/CS 추적이 쉬워진다.

### 4. 환불 연동

현재 환불은 내부 `Payment`와 `Order` 상태만 바꾼다.  
토스 실결제 환불은 아래 순서가 필요하다.

1. 내부 주문/결제 잠금 조회
2. `provider_payment_key` 확인
3. 토스 결제 취소 API 호출
4. 토스 취소 성공 응답 확인
5. 내부 `Payment REFUNDED`, `Order CANCELED` 처리
6. 주문/직원 화면 이벤트 전파

주문 금액을 쪼개는 분할 결제는 제외한다. 따라서 초기 환불 정책은 `Payment` 단위 전체 환불로 둔다.

전체 환불:

- `Payment` 1건을 `REFUNDED` 처리
- 연결된 `PaymentOrder`의 모든 `Order`를 환불/취소 상태로 전환
- `PaymentRefund` 1건 저장

부분 환불이 필요해지는 경우에만 `payment_refunds`를 주문별 환불 상세까지 확장한다.

### 5. 웹훅

카드/간편결제 위주의 즉시 승인만 다루면 웹훅 없이도 테스트 가능하다.  
다만 운영에서는 아래 이유로 웹훅 또는 서버 재조회 보정이 필요하다.

- 승인 성공 후 프론트가 닫히는 경우
- 서버 승인 처리 중 장애가 나는 경우
- 가상계좌처럼 비동기 완료가 있는 결제수단을 추가하는 경우
- 토스와 내부 DB 상태가 어긋나는 경우

웹훅을 추가하면 토스 보안키 검증, 이벤트 중복 처리, 멱등성 키 정책을 함께 설계해야 한다.

### 6. 전체 결제와 선택 결제

테이블 후불 결제에서는 여러 `READY` 주문이 하나의 결제로 묶이는 경우가 많다. 반대로 각자 결제처럼 일부 주문만 선택해서 결제하는 경우도 현실적으로 필요하다.

표현 방식:

```text
payments 1건
payment_orders N건
orders N건
```

예시:

```text
Payment 10번: 23,000원
PaymentOrder: Payment 10번 + Order 1번 + 12,000원
PaymentOrder: Payment 10번 + Order 2번 + 9,000원
PaymentOrder: Payment 10번 + Order 3번 + 2,000원
```

이 구조가 여러 주문을 하나의 결제로 표현하는 최단거리다. 기존 주문 정보는 `orders`에 유지하고, `payment_orders`가 어떤 주문들이 특정 결제에 포함됐는지를 연결한다. 이후 결제 상세, 환불, 매출 조회는 `payments`에서 출발해 `payment_orders -> orders`로 조회하면 된다.

각자 결제 예시:

```text
Payment 11번: 12,000원
PaymentOrder: Payment 11번 + Order 1번 + 12,000원

Payment 12번: 11,000원
PaymentOrder: Payment 12번 + Order 2번 + 11,000원
```

같은 테이블 구조로 전체 결제와 각자 결제를 모두 처리할 수 있다. UI와 API에서 선택 주문 목록만 다르게 넘기면 된다.

웹소켓은 별도 복잡한 배치 이벤트를 만들기보다, 결제 성공 후 연결된 주문 수만큼 기존 `COMPLETED` 주문 변경 이벤트를 발행한다.

### 7. 멱등성과 중복 승인 방지

토스 성공 페이지가 새로고침되거나 네트워크 재시도로 승인 API가 여러 번 호출될 수 있다.

필수 방어:

- `Order`를 `PESSIMISTIC_WRITE`로 잠금 조회
- `payment_orders.order_id` 유니크 제약
- `provider_payment_key` 유니크 제약
- 토스 API 호출 시 `Idempotency-Key` 사용 검토
