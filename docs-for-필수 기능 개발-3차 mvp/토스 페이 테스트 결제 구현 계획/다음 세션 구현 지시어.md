## 반드시 지킬 설계

- 주문 금액을 쪼개는 분할 결제는 제외한다.
- 초기 환불은 Payment 단위 전체 환불을 우선한다.
- 전체 결제와 선택 결제를 모두 지원할 수 있는 도메인 구조로 간다.
- 기본 UX는 테이블의 결제 대기 주문 전체 결제다.
- 각자 결제가 필요할 수 있으므로 고객이 일부 주문만 선택 결제할 수 있는 확장 여지를 둔다.
- 주문별로 결제 버튼을 여러 번 누르도록 강제하지 않는다.
- 토스 결제창은 선택된 주문 묶음에 대해 1번만 연다.
- `Payment`는 실제 결제 1건이다.
- `PaymentOrder`는 결제 1건에 포함된 주문 연결 정보다.
- 결제 후 기준으로 `Order` 1건은 `PaymentOrder` 1건과 1:1이다.
- `payment_orders.order_id`에는 유니크 제약을 둔다.
- 결제 성공 후 연결된 주문 수만큼 기존 주문 변경 이벤트 `COMPLETED`를 발행한다.
- 주방은 조리 완료까지만 관여하므로 별도 결제 전용 웹소켓 채널을 만들지 않는다.

## 구현 순서

1. 백엔드 결제 도메인 리팩터링
   - 기존 `Payment`는 삭제하지 말고 결제 헤더로 리팩터링한다.
   - `payments.order_id` 직접 FK/unique 구조를 제거하는 방향으로 설계한다.
   - `PaymentOrder` 엔티티와 `payment_orders` 테이블을 추가한다.
   - `PaymentRefund` 엔티티와 `payment_refunds` 테이블은 최소 구조로 추가한다.

2. 백엔드 토스 테스트 결제 API 추가
   - `GET /api/customer/payments/config`
   - `POST /api/customer/payments/toss/confirm`
   - 서버에서 선택된 `READY` 주문들의 금액 합계를 계산한다.
   - 전체 결제는 `READY` 주문 전체를 선택 주문 목록으로 처리한다.
   - 선택 결제는 요청으로 받은 주문 id 목록만 처리한다.
   - 토스 리다이렉트 금액과 DB 합계를 비교한다.
   - 토스 승인 API 호출은 서버에서만 수행한다.
   - 승인 성공 시 `Payment` 1건, `PaymentOrder` N건 저장 후 주문 N건을 `COMPLETED`로 전환한다.

3. 프론트 고객 키오스크 연결
   - 현재 결제 다이얼로그를 유지한다.
   - 기본은 `READY` 주문 전체 결제다.
   - 선택 결제 UI를 붙일 경우 선택된 주문만 결제 대상으로 사용한다.
   - `테스트 결제하기` 클릭 시 토스 SDK 결제창을 연다.
   - 성공 페이지에서 백엔드 confirm API를 호출한다.
   - 실패 페이지에서 실패/취소 내용을 보여준다.

4. 검증
   - 주문 1건 결제 성공
   - 주문 여러 건 합산 결제 성공
   - 일부 주문 선택 결제 성공
   - 결제 후 주문들이 모두 `COMPLETED` 전환
   - 고객/직원 화면에서 결제 완료 반영
   - 매출 요약에 결제 1건 금액 반영
   - 중복 confirm 호출 방지
