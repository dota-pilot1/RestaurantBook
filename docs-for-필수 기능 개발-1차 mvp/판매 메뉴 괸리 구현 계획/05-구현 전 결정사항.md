# 구현 전 결정사항

## 지금 바로 결정할 것

### 1. 가격 타입

MVP에서는 `integer`를 사용한다.

```txt
price integer
```

이유:

- 원화 기준 소수점이 필요 없다.
- 계산과 표시가 단순하다.

### 2. 카테고리 없는 메뉴 허용 여부

MVP에서는 허용한다.

```txt
category_id null
```

이유:

- 카테고리 생성 전에 메뉴를 임시 등록할 수 있다.
- 운영자가 정리 중인 메뉴를 보관하기 쉽다.

프론트에서는 `미분류`로 표시한다.

### 3. 삭제 방식

MVP에서는 물리 삭제.

주문 도메인 연결 이후에는 숨김 처리로 바꾼다.

### 4. 이미지 저장

이미지 파일 자체는 S3에 저장하고, 판매 메뉴에는 URL만 저장한다.

```txt
image_url
```

기존 공통 업로드 API를 재사용한다.

### 5. 판매 상태와 노출 상태

둘 다 둔다.

```txt
status: ACTIVE | SOLD_OUT | HIDDEN
visible: boolean
```

운영 UI에서는 다음처럼 표시한다.

- 판매중
- 품절
- 숨김
- 노출 꺼짐

## 추후로 미룰 것

### 옵션

예:

- 맵기
- 사이즈
- 토핑
- 음료 선택

별도 도메인으로 미룬다.

```txt
sale_menu_option_group
sale_menu_option
```

### 가격 이력

주문 연동 후 필요하다.

주문에는 반드시 주문 당시 가격 스냅샷을 저장해야 한다.

### 세트 메뉴

단순 메뉴 CRUD 이후 별도 설계한다.

### 재고

수량 기반 재고는 품절 토글과 다르다.

초기에는 수동 품절만 구현한다.

## 구현 판단

지금은 본격 CRUD 및 UI/UX 구현에 들어가도 된다.

단, 순서는 반드시 백엔드 도메인과 API를 먼저 잡고 프론트를 붙인다.

프론트부터 만들면 상태/노출/카테고리 기준이 흔들릴 가능성이 높다.
