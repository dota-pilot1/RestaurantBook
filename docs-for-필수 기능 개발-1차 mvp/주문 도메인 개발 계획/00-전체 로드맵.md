# 주문 도메인 개발 전체 로드맵

## 결론

다음 단계는 고객 키오스크 장바구니를 실제 주문으로 저장하는 것이다.

현재 구현 상태:

```txt
고객 화면 실제 메뉴 조회 완료
세트 탭 / 단품 카테고리 탭 분리 완료
장바구니 key = type + id 완료
결제하기 버튼은 아직 저장 API 미연동
```

이제 `POST /api/customer/orders`를 추가해서 장바구니를 주문으로 저장한다.

핵심 원칙:

```txt
프론트 요청 = type + id + quantity만 전달
가격/이름/구성 = 서버에서 현재 DB 기준으로 재조회
주문 저장 = 주문 당시 스냅샷 저장
세트 = 주문 상품 1줄 + 구성 품목 스냅샷
결제 연동 = 이번 단계 제외
```

## 도메인 경계

주문 도메인은 판매 메뉴 도메인과 분리한다.

판매 메뉴:

- 관리자가 편집하는 기준 데이터
- 현재 판매 상태, 노출 여부, 가격, 구성 관리
- 변경될 수 있는 데이터

주문:

- 고객이 특정 시점에 제출한 거래 데이터
- 주문 당시 상품명, 가격, 세트 구성을 보존해야 함
- 판매 메뉴가 나중에 바뀌어도 과거 주문이 깨지면 안 됨

따라서 주문은 `sale_menus`, `sale_menu_sets`를 직접 참조하되, 표시/정산에 필요한 값은 `order_items`, `order_item_components`에 스냅샷으로 저장한다.

## MVP 범위

포함:

- 고객 주문 생성 API
- 단품/세트 혼합 주문 저장
- 주문 당시 상품명/가격/수량/라인합계 저장
- 세트 구성 품목 스냅샷 저장
- 매장/포장 주문 유형 저장
- 주문 총액 서버 계산
- 품절/숨김/주문 유형 가능 여부 서버 검증
- 고객 페이지 `결제하기` 클릭 시 주문 생성 호출
- 주문 성공 후 장바구니 초기화와 간단한 성공 안내

제외:

- 실제 결제 승인/취소
- 테이블 번호/호출벨/픽업 번호 고도화
- 쿠폰/할인/포인트
- 주문 취소/환불
- 주방 보드 상태 변경
- 재고 차감
- 로그인 고객 주문 이력 연결

## 구현 순서

1. 주문 상태/유형/아이템 타입을 정리한다.
2. 백엔드 주문 엔티티와 테이블을 추가한다.
3. 주문 생성 DTO와 응답 DTO를 추가한다.
4. `OrderService`에서 상품 재조회, 주문 가능 검증, 스냅샷 저장을 구현한다.
5. `POST /api/customer/orders`를 비로그인 허용으로 추가한다.
6. 프론트 주문 엔티티/API를 추가한다.
7. `KioskHome`의 `결제하기` 버튼에서 주문 생성 API를 호출한다.
8. 주문 성공/실패/중복 클릭 방지 UI를 붙인다.
9. 빌드와 서버 테스트를 실행한다.

## 완료 기준

- 고객이 장바구니에 단품과 세트를 함께 담아 주문을 저장할 수 있다.
- 프론트가 보낸 가격이 아니라 서버가 재계산한 금액이 저장된다.
- 세트 주문은 `order_items`에는 세트 1줄로 저장된다.
- 세트 구성은 `order_item_components`에 주문 당시 이름/수량으로 저장된다.
- 품절/숨김/주문 유형 불가 상품은 주문 생성 시 거절된다.
- 주문 성공 후 고객 화면 장바구니가 비워진다.
- `npm run build`, `./gradlew test`가 통과한다.
