# 백엔드 주문 도메인 및 테이블 설계

## 패키지

신규 패키지:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/order
```

하위 구조:

```txt
order
├── application
├── domain
├── infrastructure
└── presentation
    └── dto
```

## 테이블

### orders

주문 헤더 테이블.

```txt
id bigint pk
order_no varchar(40) not null unique
order_type varchar(20) not null
status varchar(30) not null
total_amount integer not null
created_at timestamp not null
updated_at timestamp not null
```

필드 의미:

- `order_no`: 고객/운영 화면에 보여줄 주문 번호
- `order_type`: `DINE_IN`, `TAKEOUT`
- `status`: MVP에서는 `RECEIVED`로 시작
- `total_amount`: 서버가 계산한 총 주문 금액

MVP에서는 `user_id`, `table_no`, `payment_id`를 넣지 않는다.

### order_items

주문 상품 스냅샷 테이블.

```txt
id bigint pk
order_id bigint fk orders.id not null
item_type varchar(30) not null
sale_menu_id bigint null
sale_menu_set_id bigint null
item_name varchar(100) not null
unit_price integer not null
quantity int not null
line_total integer not null
display_order int not null
```

`item_type`:

```txt
SALE_MENU
SALE_MENU_SET
```

규칙:

- `SALE_MENU`이면 `sale_menu_id`만 채운다.
- `SALE_MENU_SET`이면 `sale_menu_set_id`만 채운다.
- `item_name`, `unit_price`는 주문 당시 스냅샷이다.
- `line_total = unit_price * quantity`로 서버에서 계산한다.

### order_item_components

세트 구성 스냅샷 테이블.

```txt
id bigint pk
order_item_id bigint fk order_items.id not null
sale_menu_id bigint null
component_name varchar(100) not null
quantity int not null
display_order int not null
```

규칙:

- `SALE_MENU_SET` 주문 상품에만 생성한다.
- 구성 품목의 `quantity`는 세트 1개 기준 수량이다.
- 세트 주문 수량이 2여도 component quantity는 세트 구성 그대로 저장한다.
- 실제 총 구성 수량이 필요하면 `order_item.quantity * order_item_component.quantity`로 계산한다.

## enum

신규:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/order/domain/OrderStatus.java
restaurant-book-server/src/main/java/com/cj/restaurantbook/order/domain/OrderItemType.java
```

`OrderStatus` MVP:

```txt
RECEIVED
```

후속 확장:

```txt
COOKING
READY
COMPLETED
CANCELED
```

`OrderItemType`:

```txt
SALE_MENU
SALE_MENU_SET
```

주문 유형은 이미 고객 상품 조회에 쓰는 `CustomerOrderType`이 있다. 다만 주문 도메인 내부 이름으로는 `OrderType`이 더 자연스럽다.

권장:

```txt
order/domain/OrderType.java
DINE_IN
TAKEOUT
```

이후 `customer_menu.domain.CustomerOrderType`과 중복이 거슬리면 공통 enum으로 정리한다. MVP에서는 주문 도메인 독립성을 우선한다.

## Repository

신규:

```txt
restaurant-book-server/src/main/java/com/cj/restaurantbook/order/infrastructure/OrderRepository.java
```

기본:

- `JpaRepository<Order, Long>`
- 주문 번호 중복 확인이 필요하면 `existsByOrderNo(String orderNo)` 추가

`OrderItem`, `OrderItemComponent`는 `Order` aggregate 내부 cascade로 저장한다. 별도 repository는 MVP에서 만들지 않는다.

## 검증 규칙

주문 생성 시 서버에서 반드시 검증한다.

공통:

- 주문 item 목록은 1개 이상
- quantity는 1 이상
- 같은 `itemType + id`가 중복되면 수량 합산 또는 요청 거절

MVP 권장:

```txt
중복 item은 요청 거절보다 서버에서 수량 합산
```

단품:

- `visible = true`
- `status = ACTIVE`
- 주문 유형이 `DINE_IN`이면 `availableDineIn = true`
- 주문 유형이 `TAKEOUT`이면 `availableTakeout = true`

세트:

- `visible = true`
- `status = ACTIVE`
- 주문 유형 가능 여부 확인
- 구성 품목이 1개 이상

가격:

- 프론트 가격은 받지 않는다.
- `unitPrice`, `lineTotal`, `totalAmount`는 서버에서 계산한다.
