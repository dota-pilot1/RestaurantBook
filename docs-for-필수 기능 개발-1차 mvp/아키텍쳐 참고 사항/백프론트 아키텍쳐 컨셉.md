# 백/프론트 아키텍쳐 컨셉

## 현재 단계 판단

지금은 본격적으로 RestaurantBook 도메인 설계를 시작해도 되는 단계다.

이미 인증, 인가, 역할/권한, 사용자 관리, 메뉴 관리, 사이트 설정, 업로드 같은 공통 운영 기반이 잡혀 있다. 화면도 키오스크 주문 UX의 초안이 있으므로, 이제부터는 `식당 주문/상품/재고/결제` 도메인을 어떤 경계로 나눌지 정하고 작게 구현해 나가면 된다.

단, BeautyBook처럼 모든 도메인을 한 번에 크게 깔기보다는, 초반에는 얇은 DDD와 FSD를 유지하는 편이 낫다. 구조는 명확하게 잡되, 아직 정책이 단순한 기능에는 과한 추상화를 넣지 않는다.

## 참고 기준

이 문서는 `/Users/terecal/beauty-book-hair`의 실제 구조를 기준으로 삼는다.

BeautyBook에서 검증된 큰 방향:

- Backend: 바운디드 컨텍스트별 `application / domain / infrastructure / presentation` 4계층
- Frontend: `app / widgets / features / entities / shared` 중심의 FSD
- 공통 기반: 인증, RBAC, 메뉴, 업로드, i18n, 테마, 관리자 UI는 도메인 기능과 분리
- 기능 자산화: 예약, 게시판, 근무시간, 에디터처럼 재사용 가능한 기능은 컨텍스트 단위로 유지

RestaurantBook은 이를 그대로 복제하지 않고, 식당 도메인에 맞게 아래처럼 축소 적용한다.

## Backend 컨셉

### 기본 방향

Spring Boot 서버는 BeautyBook과 같은 패키지 기준을 유지한다.

```text
com.cj.restaurantbook/
├── auth/
├── user/
├── role/
├── permission/
├── permission_category/
├── menu/
├── site_settings/
├── product/
├── order/
├── inventory/
├── payment/
├── kitchen/
└── common/
```

각 도메인 컨텍스트는 기본적으로 다음 4계층을 가진다.

```text
product/
├── presentation/      # Controller, request/response DTO
├── application/       # 유스케이스, 트랜잭션, 정책 조합
├── domain/            # Entity, Enum, 도메인 규칙
└── infrastructure/    # Repository, 외부 연동 구현
```

### 계층 역할

| 계층 | 역할 | 넣을 것 |
| --- | --- | --- |
| `presentation` | HTTP 입출력 경계 | Controller, Request DTO, Response DTO |
| `application` | 유스케이스 실행 | Service, 트랜잭션, 권한 확인, 여러 Repository 조합 |
| `domain` | 핵심 상태와 규칙 | JPA Entity, Enum, 생성/변경 메서드 |
| `infrastructure` | 저장소와 외부 구현 | Spring Data Repository, PG/알림/외부 API adapter |

초기에는 `domain service`, `factory`, `event`, `adapter interface`를 무리하게 만들지 않는다. 같은 규칙이 여러 application service에서 반복되거나 외부 연동 교체 가능성이 실제로 생길 때 추가한다.

### RestaurantBook 추천 컨텍스트

#### `product`

키오스크 메뉴와 쇼핑몰 반찬 상품을 함께 다루는 상품 컨텍스트다.

초기 추천은 메뉴와 상품을 완전히 분리하지 않고 공통 `Product`로 시작하는 것이다.

```text
Product
- name
- description
- price
- productType: MEAL, SIDE_DISH, DRINK, SET
- salesChannels: KIOSK, ONLINE, OFFLINE_POS
- saleStatus: ON_SALE, SOLD_OUT, HIDDEN
- stockTracked
- displayOrder
```

필요 테이블:

- `product_categories`
- `products`
- `product_options`
- `product_option_groups`
- `product_images`

#### `order`

키오스크 주문, 온라인 주문, 오프라인 POS성 판매 기록을 묶는 주문 컨텍스트다.

```text
Order
- orderNo
- channel: KIOSK, ONLINE, OFFLINE_POS
- orderType: DINE_IN, TAKEOUT, DELIVERY
- status: CREATED, PAID, ACCEPTED, COOKING, READY, COMPLETED, CANCELED
- totalAmount
- tableNo / pickupNo
```

필요 테이블:

- `orders`
- `order_items`
- `order_item_options`
- `order_status_histories`

주문 상태 변경은 `OrderService`에서 처리하고, 상태 전이 규칙은 `Order` 도메인 객체 안에 둔다.

#### `inventory`

재고 차감과 보정을 담당한다.

초기에는 원재료 재고까지 가지 말고 상품 단위 재고로 시작한다. 키오스크와 온라인 쇼핑몰이 같은 `Product` 재고를 바라보게 하는 것이 우선이다.

필요 테이블:

- `inventory_stocks`
- `inventory_transactions`

거래 타입:

- `ORDER_DEDUCT`
- `ORDER_CANCEL_RESTORE`
- `MANUAL_ADJUST`
- `INITIAL_STOCK`

#### `payment`

MVP에서는 실제 PG 결제보다 결제 상태 기록을 먼저 둔다.

```text
Payment
- orderId
- method: CASH, CARD, QR, PG
- status: PENDING, PAID, FAILED, CANCELED, REFUNDED
- paidAmount
- approvedAt
```

PG 연동 전에는 `수동 결제 완료`, `QR 간편결제 자리 표시자`, `현장 카드 결제 완료 처리` 정도로 충분하다.

#### `kitchen`

주방 보드는 별도 테이블이 꼭 필요하지 않을 수 있다.

초기에는 `order`의 상태를 주방 화면에서 조회하고 변경하는 방식으로 시작한다. 주방 전용 정책이 커지면 `kitchen` 컨텍스트를 분리한다.

예:

- 접수 대기 주문 조회
- 조리중 변경
- 준비 완료 변경
- 픽업/서빙 완료 변경

### 컨텍스트 분리 기준

아래 조건 중 2개 이상이면 별도 컨텍스트로 분리한다.

- 데이터 생명주기가 다르다.
- 상태 전이 규칙이 따로 있다.
- 담당 화면/권한이 다르다.
- 나중에 다른 프로젝트로 떼어갈 수 있다.
- 테스트하고 싶은 정책 단위가 독립적이다.

예를 들어 `product`와 `order`는 분리한다. 상품은 관리자가 천천히 편집하는 기준 데이터이고, 주문은 고객/키오스크/주방이 빠르게 생성하고 상태를 바꾸는 거래 데이터이기 때문이다.

### Backend 구현 원칙

- Controller에서는 비즈니스 판단을 하지 않는다.
- Service는 한 유스케이스의 트랜잭션 경계가 된다.
- Entity에는 상태 변경 메서드를 둔다. 단순 setter 남발은 피한다.
- Repository는 `infrastructure`에 둔다.
- DTO는 `presentation/dto` 아래에 둔다.
- 컨텍스트 간 직접 Entity 참조는 허용하되, 복잡해지면 ID 참조나 조회 DTO로 낮춘다.
- 공통 응답, 예외, 업로드, 인증 보안은 `common`, `auth`, `config`에 유지한다.

## Frontend 컨셉

### 기본 방향

Next.js App Router는 BeautyBook처럼 FSD 기준을 유지한다.

```text
restaurant-book-front/src/
├── app/              # 라우트, layout, provider
├── widgets/          # 페이지 여러 곳에서 쓰는 복합 UI
├── features/         # 사용자의 행동 단위
├── entities/         # 도메인 데이터, API, 타입, query hook
└── shared/           # 공통 UI, API client, lib, i18n
```

### 레이어 역할

| 레이어 | 역할 | 예시 |
| --- | --- | --- |
| `app` | URL과 페이지 조립 | `/customer`, `/kitchen`, `/products`, `/orders` |
| `widgets` | 여러 feature/entity를 조합한 큰 UI | Header, RoleHome, KitchenOrderBoard |
| `features` | 사용자의 행동/업무 단위 | kiosk-order, product-management, order-status-change |
| `entities` | 도메인 데이터 접근 | productApi, orderApi, inventoryApi, types |
| `shared` | 도메인 모르는 공통 코드 | Button, axios, tokenStorage, i18n |

### RestaurantBook 추천 구조

```text
src/
├── app/
│   ├── customer/
│   ├── kitchen/
│   ├── products/
│   ├── orders/
│   └── inventory/

│   └── kitchen-order-board/
├── features/
│   ├── kiosk/
│   ├── product-management/
│   ├── order-management/
```

### FSD 의존 방향

의존은 아래 방향으로만 흐르게 한다.

```text
app -> widgets -> features -> entities -> shared
```

허용:

- `features/kiosk`가 `entities/product`, `entities/order`를 사용
- `widgets/kitchen-order-board`가 `features/kitchen-order`와 `entities/order`를 조합
- `app/kitchen/page.tsx`가 `widgets/kitchen-order-board`를 렌더링

피할 것:

- `entities`가 `features`를 import
- `shared`가 특정 도메인 타입을 import
- `app` 페이지 안에 API 호출과 복잡한 상태 변경 로직을 직접 작성
- 한 feature가 다른 feature 내부 파일을 깊게 import

### API와 타입 배치

각 entity는 최소한 아래 구조를 가진다.

```text
entities/product/
├── api/
│   └── productApi.ts
└── model/
    ├── types.ts
    └── useProducts.ts
```

규칙:

- 서버 DTO와 맞닿은 타입은 `entities/*/model/types.ts`에 둔다.
- axios 호출 함수는 `entities/*/api/*Api.ts`에 둔다.
- TanStack Query hook은 `entities/*/model/use*.ts`에 둔다.
- 화면 전용 상태는 `features/*/model` 또는 해당 컴포넌트 내부에 둔다.

### 페이지별 배치 예시

#### 키오스크 주문

```text
app/customer/page.tsx
features/kiosk/KioskHome.tsx
features/cart/
entities/product/
entities/order/
```

초기에는 현재 `features/kiosk/KioskHome.tsx`처럼 한 파일에서 시작해도 된다. 다만 API 연동이 들어가면 메뉴 데이터는 `entities/product`, 주문 생성은 `entities/order`로 내려야 한다.

#### 주방 보드

```text
app/kitchen/page.tsx
widgets/kitchen-order-board/
features/kitchen-order/
entities/order/
```

주방 보드는 주문 목록 조회와 상태 변경을 조합하는 화면이다. 목록 UI는 widget, 상태 변경 버튼/액션은 feature, 주문 타입/API는 entity로 둔다.

#### 상품 관리

```text
app/products/page.tsx
features/product-management/
entities/product/
entities/inventory/
```

상품 등록/수정 폼은 feature, 상품/옵션/카테고리 API는 entity에 둔다.

## BeautyBook에서 가져올 점과 조심할 점

### 가져올 점

- 컨텍스트별 4계층 패키지 구조
- FSD 레이어 분리
- 권한/RBAC, Header, Guard, i18n, Theme 같은 공통 기반 유지
- 기능이 커져도 `reservation`, `board`, `schedule`처럼 도메인 단위로 찾기 쉬운 구조
- 화면은 `app`에서 얇게 조립하고 실제 업무 UI는 `features`나 `widgets`로 이동

### 조심할 점

- BeautyBook은 운영 기능이 많이 붙은 뒤의 결과물이다. RestaurantBook 초기에 그 복잡도를 모두 가져오면 개발 속도가 떨어진다.
- 처음부터 이벤트, CQRS, 도메인 서비스, adapter interface를 모두 깔 필요는 없다.
- `kitchen`은 처음부터 별도 DB 모델로 분리하지 말고, 주문 상태 기반 화면으로 시작한다.
- `payment`는 PG 연동 전까지 상태 기록 중심으로 둔다.
- `inventory`는 원재료/레시피 재고가 아니라 상품 단위 재고로 시작한다.

## 추천 구현 순서

1. `product` 컨텍스트 설계
   - 상품 카테고리, 상품, 옵션, 이미지, 판매 채널, 판매 상태

2. 관리자 상품 관리
   - 기존 관리자 UI, 권한, 업로드 API 재사용

3. `order` 컨텍스트 설계
   - 주문, 주문 항목, 옵션, 주문 상태 전이

4. 키오스크 주문 API 연동
   - 상품 조회, 장바구니, 주문 생성

5. 주방 보드
   - 주문 조회, 조리 상태 변경, 완료 처리

6. `inventory` 최소 구현
   - 주문 완료/취소 시 상품 재고 차감/복구

7. `payment` 최소 구현
   - 수동 결제 완료, QR/카드 자리 표시자, 추후 PG 확장점

8. 온라인 쇼핑몰
   - 상품 목록/상세, 장바구니, 주문, 배송 상태

## 한 줄 원칙

BeautyBook의 구조는 가져오되, BeautyBook의 현재 복잡도까지 가져오지는 않는다.

RestaurantBook은 `상품 -> 주문 -> 주방 -> 재고 -> 결제 -> 쇼핑몰` 순서로 도메인을 키우고, 각 기능이 커질 때마다 BeautyBook처럼 컨텍스트와 FSD 레이어 안에서 정리한다.
