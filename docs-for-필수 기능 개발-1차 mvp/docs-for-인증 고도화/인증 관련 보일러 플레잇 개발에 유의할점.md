# 인증 관련 보일러플레이트 개발에 유의할 점

## 목표

인증 기능은 여러 프로젝트에서 재사용할 수 있어야 하지만, 프로젝트별 정책까지 한 덩어리로 고정하면 나중에 확장이 어렵다.

보일러플레이트로 가져갈 부분과 프로젝트별로 남겨야 할 부분을 분리한다.

## 보일러플레이트로 가져갈 것

- `users`는 서비스 회원만 표현한다.
- 이메일, 전화번호, 소셜 로그인 같은 로그인 수단은 `auth_accounts`로 분리한다.
- 인증코드, 인증링크, SMS OTP 기록은 `auth_verifications`로 분리한다.
- `auth_accounts`는 `provider_type + identifier` 유니크 제약을 둔다.
- 비밀번호와 인증코드는 원문 저장하지 않고 해시만 저장한다.
- JWT subject는 이메일이 아니라 `userId`를 사용한다.
- refresh token은 사용자 기준으로 저장하고 회전한다.
- 이메일 가입 흐름은 `send-code -> verify-code -> verifiedToken -> signup`으로 둔다.
- 나중에 SMS 가입으로 바꿀 수 있도록 내부 용어는 `providerType`, `identifier`, `destination`처럼 일반화한다.

## 프로젝트별로 남겨야 할 정책

- 첫 가입자를 `ROLE_ADMIN`으로 만들지 여부
- 기본 가입 롤 코드
- 가입 성공 후 자동 로그인할지, 로그인 화면으로 보낼지
- 가입 성공 후 이동 경로
- 사용자명 필수 여부와 검증 규칙
- 이메일/전화번호 중 어떤 가입 수단을 먼저 노출할지
- 인증코드 메일 제목과 본문 문구
- 사이트 브랜드명, 발신자명
- CORS 허용 origin
- 기존 DB에서 `users.email/password_hash`를 백필하는 마이그레이션 방식

## 개발용 우회 옵션

로컬 개발에서는 실제 SMTP/SMS 연동이 급하지 않을 수 있다.

이 경우 개발용 bypass code를 둔다.

```yaml
auth:
  email-verification:
    log-only: true
    dev-bypass-code: "1234"
```

역할:

- `log-only: true`: 실제 메일 발송 대신 서버 로그에 인증코드를 출력한다.
- `dev-bypass-code`: 이 값으로 인증코드를 입력하면 실제 코드와 달라도 인증을 통과시킨다.

주의:

- 운영 환경에서는 반드시 꺼야 한다.
- 운영 배포 기본값은 빈 값이 안전하다.
- 보일러플레이트 문서에는 개발용이라고 명확히 적는다.
- 프론트 기본값으로 `1234`를 넣는 것은 로컬 개발 UX용이다. 운영 빌드에서는 제거하거나 환경 조건으로 분기한다.

운영 예시:

```yaml
auth:
  email-verification:
    log-only: false
    dev-bypass-code: ""
```

## 실제 메일 발송

로컬에서도 Gmail SMTP 발송은 가능하다.

필요 조건:

- Gmail 계정
- Google 2단계 인증
- Gmail 앱 비밀번호
- `MAIL_USERNAME`
- `MAIL_PASSWORD`

주의:

- Gmail 일반 비밀번호로는 발송되지 않는다.
- SMTP 587 포트가 네트워크에서 막힐 수 있다.
- Gmail 발송 제한에 걸릴 수 있다.
- 발신자 주소는 Gmail 계정 또는 허용된 주소와 맞추는 편이 안전하다.

## API 계약

권장 API:

```text
POST /api/auth/email/send-code
POST /api/auth/email/verify-code
POST /api/auth/signup
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/auth/me
```

`verify-code` 응답:

```json
{
  "verifiedToken": "...",
  "expiresInSec": 600
}
```

`signup` 요청:

```json
{
  "email": "user@example.com",
  "password": "password123",
  "username": "홍길동",
  "verifiedToken": "..."
}
```

주의:

- `verifiedToken`은 짧은 수명을 둔다.
- `verifiedToken`에는 provider type과 identifier를 포함한다.
- signup 시 요청 이메일과 verified token의 identifier가 같아야 한다.
- 이메일 화면이어도 서버 내부는 `auth_accounts.provider_type=EMAIL` 기준으로 조회한다.

## 스키마 설계 주의점

`users`:

- `email`을 필수 컬럼으로 두지 않는다.
- `password_hash`를 필수 컬럼으로 두지 않는다.
- 예약, 주문, 게시글 같은 도메인은 계속 `user_id`만 참조한다.

`auth_accounts`:

- `provider_type`
- `identifier`
- `password_hash`
- `verified`
- `verified_at`
- `user_id`

`auth_verifications`:

- `verification_type`
- `destination`
- `code_hash`
- `expires_at`
- `verified_at`
- `attempt_count`
- optional `auth_account_id`

## 기존 프로젝트 전환 시 주의점

이미 `users.email/password_hash` 구조로 운영 중인 프로젝트는 바로 컬럼을 삭제하면 안 된다.

전환 순서:

1. `auth_accounts`, `auth_verifications`를 추가한다.
2. 기존 `users.email/password_hash`를 `auth_accounts`로 백필한다.
3. 로그인/가입 로직을 `auth_accounts` 기준으로 바꾼다.
4. 응답 DTO의 `email`은 필요한 동안 `auth_accounts`에서 계산해서 내려준다.
5. 충분히 검증한 뒤 legacy 컬럼 제거를 별도 마이그레이션으로 처리한다.

주의:

- JPA `ddl-auto:update`만으로 `NOT NULL` 완화나 컬럼 삭제를 기대하지 않는다.
- 운영에서는 Flyway/Liquibase 같은 명시적 마이그레이션을 쓰는 편이 낫다.
- RestaurantBook의 전환용 보정 코드 같은 것은 일반 보일러플레이트에 기본 포함하지 말고 옵션으로 둔다.

## 프론트 구현 주의점

권장 흐름:

```text
이메일 입력
-> 인증코드 발송
-> 인증코드 입력
-> 인증 완료
-> 사용자명/비밀번호 입력
-> 가입
```

주의:

- 이메일이 바뀌면 인증 상태와 `verifiedToken`을 초기화한다.
- 인증 전에는 가입 버튼을 비활성화한다.
- 인증 전 사용자명/비밀번호 입력을 막을지 여부는 UX 정책으로 둔다.
- 개발용 `1234` 기본값은 운영에서 제거하거나 환경 조건으로 분기한다.
- 가입 성공 후 자동 로그인할지 여부는 프로젝트 정책으로 둔다.

## 보안 체크리스트

- 인증코드 원문을 DB에 저장하지 않는다.
- 인증코드 만료 시간을 둔다.
- 인증 실패 횟수 제한을 둔다.
- 같은 이메일 재발송 제한 또는 rate limit을 고려한다.
- `provider_type + identifier` 유니크 제약을 둔다.
- 인증 API는 `permitAll`에 넣되, 그 외 API는 인증을 요구한다.
- JWT access token에는 민감정보를 넣지 않는다.
- refresh token은 DB에 저장하고 rotate한다.
- 개발용 bypass code는 운영에서 반드시 비활성화한다.
- SMTP 비밀번호는 repository에 커밋하지 않는다.

## 보일러플레이트화 판단 기준

넣어도 되는 것:

- 인증 도메인 구조
- 공통 API 흐름
- 공통 DTO
- 공통 보안 예외
- 로컬 개발용 log-only/bypass 옵션
- provider 확장 구조

넣으면 안 되는 것:

- 특정 프로젝트 브랜드 문구
- 특정 프로젝트 롤 정책
- 특정 프로젝트 라우팅
- 특정 프로젝트 DB 전환용 임시 마이그레이션
- 실제 Gmail 계정, 앱 비밀번호, 발신자 정보

- 운영 예시는 별도 문서 또는 주석으로 분리한다.

### application.yaml 반영

보일러플레이트의 `application.yaml`에는 메일 설정과 인증 설정이 들어가야 한다.

```yaml
spring:
  mail:
    host: smtp.gmail.com
    port: 587
    username: ${MAIL_USERNAME:}
    password: ${MAIL_PASSWORD:}
    properties:
      mail.smtp.auth: true
      mail.smtp.starttls.enable: true
      mail.smtp.connectiontimeout: 5000
      mail.smtp.timeout: 5000
      mail.smtp.writetimeout: 5000

auth:
  email-verification:
    code-ttl-seconds: 300
    verified-token-ttl-seconds: 600
    subject: ${APP_DISPLAY_NAME:BeautyBook} 이메일 인증코드
    from: ${MAIL_FROM:}
    log-only: ${AUTH_EMAIL_VERIFICATION_LOG_ONLY:true}
    dev-bypass-code: ${AUTH_EMAIL_VERIFICATION_DEV_BYPASS_CODE:1234}
```

운영 기본값까지 고려하면 `log-only`와 `dev-bypass-code`의 기본값을 application-local 전용으로 빼는 것이 더 안전하다.

### build.gradle 반영

Gmail SMTP를 쓰려면 서버 보일러플레이트에 mail 의존성이 필요하다.

```gradle
implementation 'org.springframework.boot:spring-boot-starter-mail'
```

`bootRun`에서 `.env`를 읽는 현재 구조는 유지할 만하다.

다만 보일러플레이트 README에 다음을 명확히 적는다.

- `./gradlew bootRun`은 서버 폴더의 `.env`를 읽는다.
- IntelliJ 실행은 `.env`를 자동으로 읽지 않을 수 있다.
- IntelliJ에서는 Run Configuration 환경변수 또는 EnvFile 플러그인이 필요하다.

### 프론트 env와 API client

`beauty-book--front/env.example.txt`에는 API URL만 있어도 동작하지만, 인증 개발 모드를 프론트에서 분기하려면 별도 공개 env가 필요하다.

예:

```env
NEXT_PUBLIC_API_URL=http://localhost:4101
NEXT_PUBLIC_AUTH_DEV_BYPASS_CODE=1234
```

주의:

- `NEXT_PUBLIC_` 값은 브라우저에 노출된다.
- 운영에서 bypass code를 프론트에 남기면 안 된다.
- 가능하면 프론트의 `1234` 기본값은 로컬 `.env.local` 또는 development 조건으로만 켠다.

`axios.ts`의 `AUTH_PATHS`도 이메일 인증 API를 포함해야 한다.

```ts
const AUTH_PATHS = [
  "/api/auth/login",
  "/api/auth/signup",
  "/api/auth/refresh",
  "/api/auth/email/send-code",
  "/api/auth/email/verify-code",
];
```

### GitHub Pages basePath

`next.config.ts`에는 `/BeautyBook` basePath가 있다.

생성 스크립트가 `/BeautyBook`을 새 프로젝트 표시명으로 치환하고 있지만, 표시명에 공백이나 한글이 들어갈 가능성을 생각하면 안전하지 않을 수 있다.

권장:

- GitHub Pages basePath는 `DISPLAY_NAME`보다 `APP_SLUG` 기반으로 만든다.

### docs도 템플릿의 일부다

`beauty-book-container`에는 구현 문서가 많이 들어 있다.

인증 구조를 `users.email/password_hash`에서 `auth_accounts/auth_verifications`로 바꾸면 아래 문서들도 같이 갱신해야 한다.

```text
docs-for-프로젝트 세팅/회원 가입 구현/
docs-for-프로젝트 세팅/로그인 구현/
docs-for-권한 관리/
보일러 플레이트 강화 방법.md
README.md
```

주의:

- 문서 예시 코드에 `userRepository.findByEmail`이 남으면 안 된다.
- 문서 예시 DTO에 `verifiedToken` 누락이 없어야 한다.
- JWT subject가 이메일이라고 설명하는 문구가 남으면 안 된다.
- `users.email/password_hash`를 정식 구조처럼 설명하면 안 된다.

### 생성 후 검증 체크리스트

새 프로젝트를 생성한 뒤 최소 아래를 확인한다.

```bash
docker compose up -d postgres

cd APP_SLUG-server
./gradlew test

cd ../APP_SLUG-front
npm install
npm run lint
npm run build
```

수동 테스트:

1. 회원가입 화면 진입
2. 이메일 입력
3. 인증코드 발송
4. 로컬 개발이면 `1234`로 인증 확인
5. 회원가입 완료
6. `/dashboard` 또는 프로젝트별 기본 화면 이동 확인
7. 새로고침 후 `/api/auth/me` restore 확인
8. 권한 필요한 페이지 접근 확인

특히 `운영 배포 시 인증 설정 체크리스트.md`에는 다음을 명시한다.

- `AUTH_EMAIL_VERIFICATION_LOG_ONLY=false`
- `AUTH_EMAIL_VERIFICATION_DEV_BYPASS_CODE=`
- `MAIL_USERNAME`, `MAIL_PASSWORD` 설정
- 강한 `JWT_SECRET`
- 운영 CORS origin
- HTTPS 환경
- refresh token 만료 정책
- DB 마이그레이션 실행 여부

## 최종 권장 구조

```text
auth
  domain
    AuthAccount
    AuthProviderType
    AuthVerification
    AuthVerificationType
    RefreshToken
  application
    AuthService
    EmailVerificationService
    VerificationSender
  infrastructure
    AuthAccountRepository
    AuthVerificationRepository
    RefreshTokenRepository
  presentation
    AuthController
    EmailVerificationController
```

처음에는 이메일만 구현하더라도 내부 구조는 SMS를 염두에 두고 설계한다.

SMS를 붙일 때 새로 필요한 것은 대체로 다음 정도여야 한다.

- `AuthProviderType.PHONE`
- `AuthVerificationType.PHONE_SIGNUP`
- SMS sender 구현체
- 전화번호 정규화 로직
- 프론트 입력 UI
