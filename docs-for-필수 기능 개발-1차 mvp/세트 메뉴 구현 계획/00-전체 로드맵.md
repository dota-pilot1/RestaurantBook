# 세트 메뉴 구현 전체 로드맵

## 결론

고객이 세트를 세트 단위로 주문하는 구조라면 `sale_menu_sets` 테이블을 별도로 두는 것이 맞다.

현재 고객 화면의 `대표 한상 세트`, `든든 점심 세트`는 단순 분류나 표시용 탭이 아니라 장바구니에 담기고 결제 금액을 만드는 주문 상품이다. 따라서 세트는 `sale_menu_category` 같은 분류도 아니고, 단품 `sale_menu`의 플래그 정도로만 보기에도 애매하다.

권장 구조:

```txt
sale_menus
- 단품 판매 메뉴

sale_menu_sets
- 주문 가능한 세트 상품

sale_menu_set_items
- 세트에 포함되는 단품 판매 메뉴

sale_menu_categories
- 단품 메뉴 분류
```

## 네이밍

이 프로젝트는 이미 `sale_menu`, `sale_menu_category`라는 네이밍을 쓰고 있으므로 `sale_sets`보다 `sale_menu_sets`가 더 일관적이다.

```txt
권장:
sale_menu_sets
sale_menu_set_items
/api/sale-menu-sets

비권장:
sale_sets
sale_set_items
```

`sale_menu_set`은 “판매 메뉴들을 묶은 세트”라는 의미가 분명하고, `sale_menu` 도메인과의 관계도 드러난다.

## 왜 별도 테이블이 맞나

세트는 아래 이유로 독립 상품 테이블이 자연스럽다.

- 고객이 세트 자체를 1개 상품으로 주문한다.
- 세트 가격은 구성 단품 가격 합계와 다를 수 있다.
- 세트 이미지/설명/판매 상태/노출 여부가 단품과 독립적이다.
- 세트 구성은 여러 단품 메뉴를 포함한다.
- 나중에 선택형 세트, 추가금, 구성 그룹 같은 전용 정책이 붙기 쉽다.

단품과 세트를 한 테이블에 넣으면 공통 속성 재사용은 되지만, 단품에는 필요 없는 구성 규칙과 세트 검증이 `sale_menu`에 섞인다. 고객 주문까지 고려하면 별도 세트 도메인이 더 읽기 쉽다.

## MVP 범위

1차 MVP에서 포함할 것:

- 세트 메뉴 CRUD
- 세트 구성 품목 관리
- 고객 키오스크에서 세트 메뉴 조회
- 세트 단위 장바구니 담기
- 주문 요청에 단품/세트 구분 포함
- 주문 저장 시 세트 구성 스냅샷 저장

1차 MVP에서 제외할 것:

- 고객이 직접 구성 품목을 고르는 선택형 세트
- 품목별 추가금
- 세트 구성 그룹
- 시간대별 세트 판매
- 재고 연동 자동 품절

## 구현 순서

1. `sale_menu_sets`, `sale_menu_set_items` 테이블과 도메인을 만든다.
2. 세트 메뉴 관리자 CRUD API를 만든다.
3. 고객 키오스크용 상품 조회 API에서 단품과 세트를 함께 내려준다.
4. 프론트 세트 메뉴 엔티티/API를 추가한다.
5. 관리자 세트 메뉴 관리 화면을 만든다.
6. 고객 키오스크 하드코딩 세트 데이터를 API 데이터로 교체한다.
7. 주문 생성 시 단품/세트 item type을 받아 주문 스냅샷을 저장한다.

## 완료 기준

- 관리자가 세트 메뉴를 생성할 수 있다.
- 관리자가 세트에 포함될 단품 판매 메뉴를 선택할 수 있다.
- 고객 키오스크가 실제 DB의 세트 메뉴를 보여준다.
- 고객이 세트 메뉴를 장바구니에 담을 수 있다.
- 주문 요청에 단품과 세트가 함께 담길 수 있다.
- 주문 상세에는 주문 당시 세트명, 세트 가격, 구성 품목명이 스냅샷으로 남는다.
