# 조리가 불필요한 판매 메뉴에 대해 접수 받았을 경우 바로 준비 완료 처리

작성일: 2026-05-08

## 목적

콜라, 식혜, 수정과처럼 주방 조리 과정이 필요 없는 판매 메뉴는 주방에서 `조리 시작` 단계를 거치지 않고 바로 `조리 완료` 상태로 넘긴다.

운영자가 매번 수동으로 우회 버튼을 누르는 방식이 아니라, 판매 메뉴 자체에 조리 필요 여부를 설정하고 주문 상태 전이가 그 값을 따르도록 한다.

## 정책

- 판매 메뉴 기본값은 `조리 필요`.
- 음료처럼 조리 과정이 없는 메뉴는 `조리 필요=false`.
- 주문이 `접수 대기(RECEIVED)`에서 주방 접수될 때 모든 주문 아이템이 조리 불필요이면 즉시 `조리 완료(READY)`가 된다.
- 주문 아이템 중 하나라도 조리 필요이면 기존처럼 `접수됨(ACCEPTED)`으로 이동한다.
- 세트 메뉴는 구성 메뉴 중 하나라도 조리 필요이면 세트 전체를 조리 필요로 본다.

## 상태 전이

### 일반 조리 주문

```text
RECEIVED -> ACCEPTED -> COOKING -> READY -> COMPLETED
```

### 조리 불필요 주문

```text
RECEIVED -> READY -> COMPLETED
```

정확히는 주방에서 `주문 접수` API를 호출하면 서버 내부에서 `ACCEPTED`로 접수한 뒤, 조리 불필요 주문이면 같은 트랜잭션 안에서 바로 `READY`로 전환한다.

## 데이터 모델

### sale_menus

`requires_cooking boolean not null default true`

판매 메뉴의 현재 조리 필요 여부를 저장한다. 메뉴 관리 화면에서 수정할 수 있다.

### order_items

`requires_cooking boolean not null default true`

주문 생성 시점의 판매 메뉴 조리 필요 여부를 스냅샷으로 저장한다.

이 스냅샷이 필요한 이유:

- 주문 후 메뉴 설정이 바뀌어도 이미 들어온 주문의 처리 규칙이 흔들리지 않아야 한다.
- 주문 보드와 이력은 주문 시점의 사실을 기준으로 봐야 한다.
- 세트 메뉴 구성 변경이 과거 주문의 조리 필요 여부를 바꾸면 안 된다.

## Seed 기준

기본 seed 메뉴 중 아래 메뉴는 `requiresCooking=false`로 설정한다.

| 메뉴 | 조리 필요 |
| --- | --- |
| 식혜 | false |
| 수정과 | false |
| 콜라 | false |

나머지 식사, 국/찌개, 면/분식, 사이드 메뉴는 기본적으로 `true`다.

## Initializer 데이터 반영

`SaleMenuSeeder`의 `MenuDef`에 `requiresCooking` 값을 추가한다.

신규 insert뿐 아니라 이미 존재하는 seed 메뉴를 update할 때도 `requiresCooking`을 다시 반영해야 한다. 그래야 기존 로컬 DB처럼 이미 메뉴가 생성된 환경에서도 서버 재시작 시 값이 보정된다.

```java
private record MenuDef(
        String categoryName,
        String name,
        String description,
        int price,
        boolean requiresCooking,
        int displayOrder
) {}
```

```java
existing.update(
        category,
        menu.name(),
        menu.description(),
        menu.price(),
        existing.getImageUrl(),
        SaleMenuStatus.ACTIVE,
        true,
        true,
        true,
        menu.requiresCooking(),
        menu.displayOrder()
)
```

현재 seed 기준:

| 카테고리 | 메뉴 | 조리 필요 |
| --- | --- | --- |
| 식사 | 육회 비빔밥, 제육 덮밥, 불고기 덮밥 | true |
| 국/찌개 | 김치 찌개, 된장 찌개, 소고기 미역국 | true |
| 면/분식 | 잔치 국수, 떡볶이 | true |
| 사이드 | 해물 파전, 김치전, 고기 만두, 오늘의 반찬 | true |
| 음료 | 식혜, 수정과, 콜라 | false |

## UI 결정

주방 주문 카드에 `접수됨 -> 조리 완료` 수동 버튼을 추가하지 않는다.

이유:

- 콜라 같은 메뉴의 처리 규칙은 주문 당시 메뉴 데이터가 판단해야 한다.
- 수동 버튼은 조리 필요한 주문도 실수로 건너뛸 수 있다.
- 운영자는 메뉴 관리에서 `조리 필요` 토글만 관리하면 된다.

## 검증 체크리스트

- [ ] 메뉴 관리에서 콜라의 `조리 필요` 토글을 끌 수 있다.
- [ ] 콜라만 담은 주문은 고객 주문 후 주방 보드에서 `접수 대기`에 표시된다.
- [ ] 주방에서 `주문 접수`를 누르면 해당 주문이 바로 `조리 완료` 컬럼으로 이동한다.
- [ ] 조리 필요한 메뉴가 하나라도 포함된 주문은 `접수됨`으로 이동한다.
- [ ] 조리 불필요 메뉴와 조리 필요 메뉴가 섞인 주문은 자동 완료되지 않는다.
- [ ] 세트 메뉴 구성 중 하나라도 조리 필요 메뉴가 있으면 자동 완료되지 않는다.
- [ ] 직원 주문 보드에서는 바로 결제 대기 주문으로 보인다.

## 운영 주의점

현재 프로젝트는 `spring.jpa.hibernate.ddl-auto: update`를 사용하므로 로컬 개발 DB는 서버 실행 시 컬럼이 자동 추가된다.

운영 DB에 적용할 때는 아래 컬럼 추가를 명시적으로 반영하는 것이 좋다.

```sql
alter table sale_menus
    add column if not exists requires_cooking boolean not null default true;

alter table order_items
    add column if not exists requires_cooking boolean not null default true;
```

이미 실행 중인 서버가 있으면 재시작해야 새 상태 전이 로직이 반영된다.
