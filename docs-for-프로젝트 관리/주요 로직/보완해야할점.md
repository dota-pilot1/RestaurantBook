# 보완해야 할 점

주문 관련 로직과 매출 관련 로직은 현재 MVP 기준으로 동작 가능한 구조다. 다만 운영 품질과 통계 정확도를 높이려면 아래 항목을 우선순위에 따라 보완하는 것이 좋다.

## 1. 매출 통계의 총매출 지표 추가 여부

현재 매출 조회는 `Payment.status = PAID`인 결제만 순매출과 결제수단별 매출에 포함한다. 환불되면 결제 상태가 `REFUNDED`로 바뀌기 때문에 기존 결제 목록과 순매출에서 빠지고, 환불 목록에는 `refundedAt` 기준으로 들어간다.

이 방식은 매장 운영자가 실제 남은 매출을 바로 보는 데 적합하다. 따라서 현재 화면에서는 이 값을 `총 매출`이 아니라 `순매출`로 표시한다.

추후 필요 시 보완 방향:

- `총 결제액`: 조회 기간에 결제된 모든 결제금액을 `paidAt` 기준으로 합산
- `순매출`: 현재처럼 환불 제외 후 남은 결제금액으로 표시
- `환불액`: 조회 기간에 환불된 금액을 `refundedAt` 기준으로 합산
- 총 결제액이 필요한지, 운영 화면에서는 순매출만으로 충분한지 결정

현재 MVP에서는 순매출과 환불액을 분리해서 보는 기준으로 충분하다.

## 2. 주문 취소와 환불 상태 구분

현재 환불 처리된 주문은 주문 상태가 `CANCELED`가 된다. 일반 취소도 `CANCELED`다. 화면에서는 취소 메시지나 결제 상태를 함께 봐야 일반 취소와 환불 취소를 구분할 수 있다.

보완 방향:

- 주문 상태에 `REFUNDED`를 추가할지 검토
- 또는 주문 상태는 유지하고 `cancelReasonType`, `canceledBy`, `refundedAt` 같은 명시 필드를 추가
- 직원/주방/고객 화면에서 “취소됨”과 “환불됨” 표현을 분리

운영자가 나중에 이력을 확인할 때 단순 취소와 결제 후 환불은 의미가 다르므로 구분하는 편이 좋다.

## 3. 결제 이력의 불변성 강화

현재 환불 시 기존 `Payment`의 상태가 `PAID -> REFUNDED`로 바뀐다. MVP에서는 단순하지만, 정산/감사 관점에서는 결제 이벤트와 환불 이벤트를 별도 이력으로 남기는 방식이 더 명확하다.

보완 방향:

- `payments`는 결제 원장을 유지하고 상태 변경만 할지 결정
- 별도 `payment_events` 또는 `refunds` 테이블을 둘지 검토
- 누가, 언제, 어떤 사유로 환불했는지 저장
- 환불 사유 입력 기능 추가

실제 매장 정산을 염두에 두면 환불 사유와 처리자 기록은 필요해질 가능성이 높다.

## 4. 결제수단 기타의 의미 구체화

현재 결제수단은 카드, 현금, 기타다. 기타는 빠르게 운영하기에는 좋지만, 시간이 지나면 의미가 모호해질 수 있다.

보완 방향:

- 기타 선택 시 메모 입력을 받을지 검토
- 계좌이체, 쿠폰, 서비스, 외상 등으로 세분화할지 검토
- 정산 화면에서 기타 내역을 별도로 확인할 수 있게 구성

지금은 `ETC` 하나로 충분하지만, 실제 운영 데이터가 쌓이면 기타 비율이 높아지는 순간 원인 파악이 어려워질 수 있다.

## 5. 직원 페이지의 매출 정보 노출 범위

직원 페이지에 결제 목록을 직접 넣으면 주문 보드의 목적이 흐려질 수 있다. 현재 구조에서는 상세 결제 목록과 통계는 매출 페이지에 두는 편이 낫다.

보완 방향:

- 직원 페이지에는 오늘 결제 건수/금액 정도의 작은 요약만 노출
- 상세 목록은 매출 페이지로 이동
- 직원 권한에서 매출 페이지 접근을 허용할지 별도 정책 결정

직원 역할이 단순 주문 처리라면 상세 매출 노출은 매니저/관리자 전용으로 유지하는 편이 자연스럽다.

## 6. 영업일 기준 정산

현재 매출 조회는 `Asia/Seoul`의 날짜 00:00부터 다음날 00:00 직전까지를 하루로 본다. 일반적인 음식점에서는 새벽 영업이 있거나 마감 시간이 자정을 넘을 수 있다.

보완 방향:

- 영업일 시작 시간을 설정값으로 분리
- 예: 영업일 기준 05:00 ~ 다음날 04:59
- 매출 통계와 오늘 요약이 같은 영업일 기준을 쓰도록 통일

운영 시간이 자정을 넘지 않는 매장이라면 지금 방식도 충분하지만, 장기적으로는 영업일 기준 설정이 필요할 수 있다.

## 7. 주문/결제 테스트 보강

현재 매출 조회 단위 테스트는 존재하지만, 주문 완료와 결제 저장이 실제로 하나의 흐름으로 이어지는 통합 테스트는 더 보강할 수 있다.

보완 방향:

- `READY` 주문 결제 완료 시 `Payment`가 저장되는 통합 테스트
- 중복 결제 완료 시 차단되는 테스트
- 환불 시 `Order`와 `Payment`가 함께 변경되는 테스트
- 매출 API에서 결제수단별 집계가 실제 DB 기준으로 맞는지 테스트

이 테스트가 있으면 주문/매출 리팩터링 시 회귀를 훨씬 빨리 잡을 수 있다.

## 8. 실시간 갱신 실패 시 보완

현재 주문/매출 화면은 웹소켓 이벤트와 쿼리 invalidate에 의존한다. 이벤트가 누락되거나 브라우저가 백그라운드에 있으면 화면 갱신이 늦을 수 있다.

보완 방향:

- 주문 보드와 매출 요약에 적절한 주기적 refetch 추가 검토
- 결제 완료/환불 성공 직후 관련 쿼리 강제 refetch 유지
- 마지막 갱신 시각 표시 검토

운영 화면은 실시간성이 중요하므로, 웹소켓과 폴링을 함께 쓰는 보수적인 방식도 고려할 수 있다.

## 9. 권한 정책 정리

현재 운영 주문 처리는 `ADMIN`, `STAFF`가 가능하고, 매출 조회는 `ADMIN`, `MANAGER`가 가능하다. 역할 구분 자체는 합리적이지만, 실제 매장 운영에서는 직원이 오늘 결제 내역을 봐야 하는지 정책이 필요하다.

보완 방향:

- 직원이 매출 상세를 볼 수 있는지 결정
- 직원에게 오늘 결제 요약만 보여줄지 결정
- 환불 권한을 직원 전체에게 줄지, 매니저 이상으로 제한할지 결정

특히 환불은 금전 처리이므로 권한을 더 엄격하게 가져갈 수 있다.
