# 주문 관련 프로세스 설명

RestaurantBook의 주문 로직은 고객 주문 생성, 주방 처리, 직원 결제 완료, 취소/환불 안내까지 이어지는 흐름이 핵심이다. 주문 자체의 상태는 `orders.status`로 관리하고, 결제 금액과 결제수단은 결제 완료 시점에 `payments`로 별도 저장한다.

## 핵심 상태

현재 주문 상태는 다음 6개다.

- `RECEIVED`: 고객이 주문을 접수한 직후
- `ACCEPTED`: 주방이 주문을 접수한 상태
- `COOKING`: 조리 중
- `READY`: 조리 완료, 직원 결제 대기
- `COMPLETED`: 직원이 결제 완료 처리한 주문 종료 상태
- `CANCELED`: 고객/주방/직원 취소 또는 결제 후 환불 처리된 상태

기본 정상 흐름은 `RECEIVED -> ACCEPTED -> COOKING -> READY -> COMPLETED`다.

조리가 필요 없는 메뉴만 포함된 주문은 주방 접수 시 `ACCEPTED`를 거쳐 바로 `READY`가 된다. 이때 직원 페이지에서는 곧바로 결제 대기 주문으로 볼 수 있다.

## 고객 주문 생성

고객 화면에서 주문을 접수하면 프론트는 주문 타입, 테이블명, 주문 상품 목록을 서버로 전달한다.

서버의 `OrderService.createCustomerOrder`는 다음 순서로 처리한다.

1. 주문 항목을 상품 타입과 상품 id 기준으로 정규화한다.
2. 동일 상품이 중복으로 들어오면 수량을 합산한다.
3. 판매 메뉴 또는 세트 메뉴의 현재 판매 가능 상태를 확인한다.
4. 주문번호를 생성한다.
5. `Order.create(...)`로 주문을 만들고 총액을 계산한다.
6. `orders`, `order_items`, `order_item_components`에 저장한다.
7. 주문 변경 이벤트 `CREATED`를 브로드캐스트한다.

고객 화면은 테이블명을 기준으로 `RECEIVED`, `ACCEPTED`, `COOKING`, `READY` 상태의 활성 주문을 조회한다. 이미 완료된 주문은 고객 활성 주문 목록에서 빠지고, 취소된 주문은 취소 메시지가 남아 있을 때 최근 취소 안내로 별도 조회된다.

## 주방 처리

주방 화면은 `RECEIVED`, `ACCEPTED`, `COOKING`, `READY` 상태의 주문을 조회한다.

주방에서 가능한 주요 동작은 다음과 같다.

- 주문 접수: `RECEIVED -> ACCEPTED`
- 조리 시작: `ACCEPTED -> COOKING`
- 조리 완료: `ACCEPTED` 또는 `COOKING -> READY`
- 취소: `COMPLETED`, `CANCELED`이 아닌 주문을 `CANCELED`로 전환

주문 접수 시 모든 항목이 조리 불필요 메뉴라면 바로 `READY`로 전환된다. 조리 필요한 메뉴가 하나라도 있으면 `ACCEPTED` 상태에 머문다.

주방에서 취소하면 취소 메시지가 주문에 저장되고, 고객/직원 화면에 취소 안내가 전파된다. 주방 취소 안내는 확인과 정리 상태를 별도로 기록한다.

## 직원 처리

직원 페이지는 운영 주문 보드 역할을 한다. 현재 보드에서는 `ACCEPTED`, `COOKING`, `READY`, `COMPLETED` 주문을 볼 수 있다.

직원 페이지에서 가장 중요한 동작은 `READY` 주문의 결제 완료 처리다.

1. 직원이 `READY` 주문에서 결제 완료를 누른다.
2. 카드, 현금, 기타 중 결제수단을 선택한다.
3. 서버의 `/api/operations/orders/{orderId}/complete`를 호출한다.
4. 서버는 주문 상태를 `READY -> COMPLETED`로 변경한다.
5. 같은 트랜잭션에서 `payments` 테이블에 결제 기록을 저장한다.
6. 주문 변경 이벤트 `COMPLETED`를 브로드캐스트한다.

즉 직원 결제 완료는 단순히 주문 상태만 바꾸는 것이 아니라, 매출 집계를 위한 `Payment` 레코드를 만드는 기준점이다.

## 취소와 환불

고객 취소는 `RECEIVED` 상태에서만 가능하다. 고객이 주문한 직후 주방이 아직 접수하지 않은 상태에서만 직접 취소할 수 있게 제한되어 있다.

운영 취소는 `COMPLETED`, `CANCELED`이 아닌 주문에서 가능하다. 즉 결제 완료 전 주문은 직원/주방 쪽에서 취소할 수 있다.

결제 완료된 주문은 일반 취소가 아니라 환불 흐름을 탄다.

1. 직원이 `COMPLETED` 주문에서 환불을 누른다.
2. 서버가 주문 상태를 `COMPLETED -> CANCELED`로 바꾼다.
3. 연결된 `Payment` 상태를 `PAID -> REFUNDED`로 바꾼다.
4. `refundedAt`, `refundedBy`를 저장한다.
5. 주문 변경 이벤트 `REFUNDED`를 브로드캐스트한다.

현재 구조에서는 환불도 주문 상태로는 `CANCELED`로 표현된다. 따라서 화면에서 단순 취소와 환불 취소를 구분하려면 `Payment.status`, 취소 메시지, 또는 별도 주문 상태 확장이 필요하다.

## 실시간 반영

주문 생성, 상태 변경, 취소, 결제 완료, 환불은 서버에서 브로드캐스트된다. 프론트는 이 이벤트를 받아 주문 관련 쿼리와 매출 관련 쿼리를 갱신한다.

주문 쿼리 갱신 대상은 주로 다음과 같다.

- 고객 활성 주문
- 고객 취소 안내
- 주방 주문 목록
- 직원 운영 주문 목록
- 결제 대기 주문 목록
- 매출 요약/상세

따라서 정상적으로 웹소켓 이벤트가 전달되면 다른 화면에서도 주문 상태 변화가 자동 반영된다. 다만 화면별로 쿼리 키와 이벤트 처리 범위가 달라질 수 있으므로, 새 화면을 만들 때는 해당 이벤트에 대한 invalidate 처리를 반드시 확인해야 한다.

## 현재 가장 중요한 주문 원칙

주문 로직에서 가장 중요한 기준은 다음 두 가지다.

- 주문 상태는 운영 진행도를 나타낸다.
- 매출은 주문 상태가 아니라 결제 완료 시 생성되는 `Payment`를 기준으로 본다.

따라서 `COMPLETED` 주문은 운영상 종료된 주문이고, 실제 매출 집계의 원천 데이터는 그 시점에 저장된 `payments` 레코드다.
