# 권한 관리 정책

RestaurantBook의 권한 정책은 10명 안팎의 소규모 식당 운영을 기준으로 잡는다. 이 규모에서는 역할을 너무 세밀하게 막기보다, 매니저가 현장 운영을 백업할 수 있게 열어두는 편이 실무에 맞다.

## 현재 정책 요약

현재 MVP 권한 정책은 “관리자는 전체 관리, 매니저는 현장 운영 백업, 직원은 홀/결제 처리, 주방은 조리 처리”로 구분한다.

- `ADMIN`: 전체 기능 접근 가능
- `MANAGER`: 매니저 대시보드, 직원 주문 보드, 주방 현황, 매출 통계, 메뉴/품절/테이블 운영 관리 가능
- `STAFF`: 직원 주문 보드, 결제 완료, 환불, 고객 호출 응대 가능
- `KITCHEN`: 주방 현황, 주문 접수, 조리 시작, 조리 완료, 주방 취소 가능
- `CUSTOMER`: 고객 키오스크 주문과 직원 호출 가능

현재 정책에서 중요한 결정은 매니저에게 `/staff`와 `/kitchen-board`를 열어두는 것이다. 10명 규모 식당에서는 매니저가 직원이나 주방 담당자의 업무를 즉시 확인하고 백업해야 하므로, 매니저가 현장 운영 페이지를 볼 수 있어야 한다.

## 기본 역할

현재 주요 역할은 다음과 같다.

- `ROLE_ADMIN`: 시스템 전체 관리자
- `ROLE_MANAGER`: 매장 운영 관리자
- `ROLE_STAFF`: 홀/직원 주문 처리 담당자
- `ROLE_KITCHEN`: 주방 주문 처리 담당자
- `ROLE_CUSTOMER`: 고객 화면 사용자

## 권한 원칙

가장 중요한 원칙은 다음과 같다.

- 관리자는 모든 기능에 접근할 수 있다.
- 매니저는 현장 운영과 매출 확인에 접근할 수 있다.
- 직원은 직원 주문 보드와 고객 호출 응대 중심으로 접근한다.
- 주방은 주방 주문 보드 중심으로 접근한다.
- 시스템 설정, 유저/역할/권한 관리는 관리자 전용으로 둔다.

10명 규모 매장에서는 매니저가 직원 업무와 주방 흐름을 확인하지 못하면 운영 백업이 어렵다. 따라서 매니저는 직원 페이지와 주방 페이지를 열람하고 필요한 운영 처리를 할 수 있게 둔다.

## 매니저 권한 기준

매니저는 현장 운영 책임자다. 따라서 다음 기능은 열어두는 것이 적절하다.

- 직원 주문 보드 접근
- 주방 현황 접근
- 결제 대기 주문 확인
- 결제 완료 처리
- 환불 처리
- 직원 호출 확인 처리
- 품절/노출 관리
- 매출 통계 확인

소규모 매장에서는 매니저가 특정 직원이나 주방 담당자 부재 시 바로 처리해야 한다. 화면 접근이 막히면 매니저 대시보드의 운영 버튼이 실제 동작하지 않는 문제가 생기므로, 매니저에게 직원/주방 화면 접근을 허용한다.

다만 장기적으로 매장이 커지면 다음 권한은 분리할 수 있다.

- 매니저의 환불 처리 권한
- 매니저의 주방 주문 상태 변경 권한
- 매니저의 직원 호출 처리 권한

현재 MVP에서는 매니저가 현장 처리를 모두 백업할 수 있게 둔다.

## 직원 권한 기준

직원은 홀 운영과 결제 처리를 담당한다.

직원에게 허용하는 기능:

- 직원 주문 보드 접근
- 결제 대기 주문 확인
- 결제 완료 처리
- 고객 호출 확인 처리
- 운영 취소 또는 환불 처리

직원에게 제한하는 기능:

- 매출 통계 상세
- 메뉴/테이블 관리
- 시스템 설정
- 유저/권한 관리

환불은 금전 처리이므로 장기적으로는 매니저 이상으로 제한할 수 있다. 현재 MVP에서는 직원 주문 보드 안에서 운영 흐름 검증이 우선이므로 직원에게도 허용한다.

## 주방 권한 기준

주방은 조리 흐름 처리를 담당한다.

주방에게 허용하는 기능:

- 주방 현황 접근
- 주문 접수
- 조리 시작
- 조리 완료
- 주방 주문 취소
- 취소 알림 확인/정리

주방에게 제한하는 기능:

- 결제 완료 처리
- 환불 처리
- 매출 통계
- 메뉴/테이블 관리
- 시스템 설정
- 유저/권한 관리

주방은 매출이나 결제보다는 조리 상태 정확성이 핵심이다.

## 관리자 권한 기준

관리자는 시스템 소유자 역할이다.

관리자 전용 기능:

- 유저 관리
- 역할 관리
- 역할-권한 매핑
- 내비게이션 메뉴 관리
- 사이트 설정
- 화면 설정
- 게시판 설정
- 전체 운영/상품/매출 관리

운영 데이터 처리뿐 아니라 시스템 구조를 바꿀 수 있는 기능은 관리자 전용으로 둔다.

## 현재 구현 반영 상태

현재 코드 기준으로 매니저는 다음 운영 화면에 접근할 수 있어야 한다.

- `/manager`
- `/staff`
- `/kitchen-board`
- `/sales`
- `/sale-menus`
- `/sale-menu-sets`
- `/sale-menu-categories`
- `/sale-menu-availability`
- `/tables`

서버 API도 같은 기준으로 맞춘다.

- 직원/운영 주문 API: `ADMIN`, `MANAGER`, `STAFF`
- 주방 주문 API: `ADMIN`, `MANAGER`, `KITCHEN`
- 직원 호출 운영 API: `ADMIN`, `MANAGER`, `STAFF`
- 매출 API: `ADMIN`, `MANAGER`

프론트 화면 가드와 서버 API 권한은 반드시 같은 방향으로 유지해야 한다. 프론트만 열고 서버가 막히면 화면은 보이지만 데이터 조회나 처리가 실패한다.

## 추후 보완할 점

현재 MVP 이후에 검토할 항목은 다음과 같다.

- 환불 권한을 `ADMIN`, `MANAGER`로 제한할지
- 매니저의 주방 상태 변경을 조회 전용으로 나눌지
- 직원의 운영 취소 권한을 제한할지
- 매출 통계 일부를 직원에게 요약만 보여줄지
- 내비게이션 메뉴 노출 권한과 API 권한을 더 엄격하게 동기화할지
- 역할별 버튼/액션 비활성화 정책을 별도 컴포넌트로 분리할지
- 권한 변경 시 화면 가드, API 권한, 내비게이션 노출이 함께 바뀌도록 테스트를 추가할지

현 단계에서는 소규모 매장 운영성과 테스트 편의성을 우선해 매니저 권한을 넓게 둔다.
